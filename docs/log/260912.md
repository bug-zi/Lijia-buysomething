## 配置库修复三：关窗检测改 RPC 往返探测 + 任意标签页跳转判定（is_closed 盲区）

> 创建于 2026-09-12 03:15

**问题（开发者实测，情绪强烈）**：淘宝扫码停在「请在手机上确认登录」不动；关闭窗口后仍「登录中」，刷新页面无效——上一修（`page.is_closed()`）**没有解决**。

**根因（上一修的盲区）**：`page.is_closed()` 与 `page.url` 都是 **Playwright 本地缓存状态**——用户直接点窗口 X 关闭（浏览器进程退出）时，close 事件可能永远不送达驱动层，二者恒为 False/旧值，轮询照旧空等 180s。修一换了检测点但没换检测性质，故无效。

**修复（`web_scraper._goto_login_and_wait` 重写轮询）**：
- **真实 RPC 往返探测**：每轮调 `page.title()`，浏览器进程已死则立刻抛错——不依赖事件送达；导航瞬间 RPC 偶发误报也可能抛错，故**连续 3 次（约 6s）失败才判关窗**，`is_closed()` 作为即时通道保留，避免误杀进行中的登录；
- **成功判定升级**：`context.pages` 内**任意标签页**跳离登录域即算成功（部分平台登录后在新标签页完成跳转，旧逻辑只盯第一页会漏判——这是「手机已确认却一直不跳」的可能代码侧因素之一）；`u.startswith("http")` 排除 about:blank/错误页误判。

**验证（mock 四分支）**：进程死亡 4s 内返回 False（原 180s 卡死）；首次探测误报后登录成功不误杀（True）；新标签页跳转（True）；原地未登录超时（False）。编译 + config_store 自测 + 导入 + demo 18 案例回归（exit=0）全过。

**通道诊断**：`_find_system_browser()` 本机返回 `chrome`（真实 Chrome 优先，淘宝指纹条件具备）；此前报错中出现捆绑 Chromium 系 profile 抢占后的回退尝试。淘宝扫码停在「手机确认」的直接原因在平台侧风控/流程（如实告知），代码侧已排除关窗漏判与新标签漏判两类因素，建议重试时在窗口内一并完成滑块/验证。

**涉及文件**：`web_scraper.py`、本文档。

## 配置库修复二：关窗即取消登录（page.url 不抛错导致假「登录中」）

> 创建于 2026-09-12 03:05

**问题（开发者实测）**：① 淘宝扫码后登录失败；② 关闭登录窗口后页面仍「登录中，请稍候」，再点京东登录被全局互斥拒绝「已有浏览器任务正在进行（淘宝/天猫·登录中）」。

**根因**：`_goto_login_and_wait`（web_scraper）靠 `page.url` 抛异常感知关窗，但 Playwright 的 `page.url` 在页面关闭后**不抛异常**、恒返回最后已知 URL——窗口关了轮询仍空等 180s 超时；期间任务表不释放，全局互斥（上一轮修复所为防 profile 抢占）如实拒绝了其他平台的登录请求。两现象同源。

**修复**：
- `web_scraper._goto_login_and_wait`：轮询首行加 `page.is_closed()` 检测，关窗即返回 False（约 2s 内释放任务）；**抓取流程的同窗口登录同样受益**（此前用户关窗也要干等超时）；
- `config_store._manual_login_worker`：失败备注如实区分「超时/窗口被关闭/平台验证未通过——如遇滑块或验证码请一并完成后重试」；
- `index.html`：「登录中」禁用按钮文案标注「关闭登录窗口即可取消」，登录 toast 同步提示。

**验证**：mock 页面双分支实测——关窗（is_closed=True）立即返回 False 且不再读 url；3 秒后模拟跳离登录域正确返回 True。三文件编译 + config_store 自测 + web_scraper 导入均通过。

## 配置库修复：浏览器任务全局互斥 + 超时自愈（开发者实测反馈）

> 创建于 2026-09-12 03:00

**问题（开发者实测）**：① 京东扫码登录一直卡「登录中」；② 随后淘宝「立即检测」直接报错 `launch_persistent_context: Target page, context or browser has been closed`（原始错误含 Chromium「已在另一会话中打开」的 GBK 乱码输出）。

**根因**：`.browser_profile` 是单实例 profile，同一时刻只能开一个浏览器；而 `config_store` 的任务表只做了**同平台**互斥（京东登录中仍允许淘宝检测并发发起），第二个浏览器抢同一 profile 必然崩溃。「登录中」卡住则是登录任务本就需等扫码（≤3 分钟）叠加无自愈机制——任务线程一旦异常滞留，界面会永久停在进行时态。

**修复（仅 `config_store.py`）**：
- **全局互斥**：检测/登录/清理三入口改为「任意任务进行中即拒绝」（`_busy_response` 带明哪个平台·什么任务 + 指引文案），profile 不再被并发抢占；
- **超时自愈**：`_JOB_TTL`（登录 330s＝启动重试 90s+跳转 30s+等扫码 180s 的最坏耗时余量；检测/清理 150s），`get_states` 与三入口先 `_expire_stale_jobs`，超时任务自动释放并如实写「任务超时」标注；
- **锁可重入**：自愈路径会在持锁状态下经 `record_state` 再入锁，`threading.Lock` 换 `RLock`（否则死锁）；
- **失败文案短句化**：`_short_err` 截取原始多行 Playwright 错误首行（≤160 字符）+ `_profile_busy_hint` 指引（先关残留窗口/等抓取结束）；
- **登录窗口置前**：worker 启动后 `page.bring_to_front()`，避免找不到待扫码窗口。

**验证**：`python config_store.py` 自测通过（新增断言：跨平台全局互斥拒绝、回拨时钟触发超时自愈释放、持锁再入不死锁）；三文件编译通过。**修复后须重启服务生效**；界面如有残留「登录中」显示，重启后自动消失（任务表在内存）。

**遗留说明**：配置库与**抓取流程**分属两模块仍无法互斥（web_scraper 搜索/详情登录窗口不经过任务表）——若抓取正占着 profile 时点检测/登录，会收到短句化失败提示，按指引稍后再试即可（如实报错，不绕过）。

**涉及文件**：`config_store.py`、本文档。

## 登录流程修复：同窗口扫码 + Patchright 下停用 stealth 注入

> 创建于 2026-09-12 01:52

**问题（开发者实测反馈）**：① 扫码登录京东一直不成功；② 后续自动启动的浏览器窗口闪现即被关闭，无法扫码；③ 希望登录一次后短期免登录。

**根因分析**：
1. **扫码被拒最大嫌疑**：Patchright 官方明确警告不要叠加自定义 stealth/init 注入脚本（破坏驱动级隐身、暴露自动化特征），而 `_launch_browser` 仍在注入 `_STEALTH_JS`；
2. **窗口闪退**：登录窗口由后台线程另开一个浏览器，与搜索浏览器抢同一个 `.browser_profile` profile 锁，互相挤掉；
3. 「登录一次短期免登」本就是 `.browser_profile` 持久化设计，登录没成功导致该能力无从体现。

**修复（仅 `web_scraper.py`）**：
- Patchright 生效时**停用 `_STEALTH_JS` 注入**（仅回退原版 Playwright 时保留）；新增 `_get_sync_playwright()` 返回当前基座标识；
- 删除后台线程版 `open_login_and_wait`，改为 `_goto_login_and_wait()`：**同一个窗口内**跳登录页原地等扫码（最长 3 分钟，轮询 URL 跳离登录域判定成功），成功后**自动重搜**，无需再回复「继续抓取」；超时/关窗才交还人工；
- `_launch_browser` 启动加重试链（真实 channel → 无 channel → 等 2s 重试），兜底 profile 短暂被占用场景。

**验证**：无残留引用；语法/导入自测通过；模拟登录超时路径交还人工正常；demo 18 案例回归通过。京东未登录页面表现仍不稳定（有时报墙有时空结果），登录态为硬前提。

**待开发者验收**：输入购物需求 → 弹出的窗口跳到登录页 → 扫码（若出现滑块一并完成）→ 等待自动重搜返回结果；登录一次后短期免扫码。

## 启动脚本重写（修复双击无响应 / cmd 报「此时不应有 >。」，全栈启动层）

> 创建于 2026-09-12 00:47

**需求来源**：开发者反馈双击 `.bat` 无响应，`cmd /c` 调用报 `此时不应有 >。`；后要求放弃修补、直接换更简单的启动方式。

**诊断过程**（多次实测复现）：

1. 原症状复现：原版网页版 bat 一执行即报 `此时不应有 >。` 并终止（解析期致命错误，pause 都执行不到，故双击表现为闪退）；
2. 纯 ASCII 最小复现不报错 → 排除 bat 逻辑本身，锁定编码问题：**bat 文件为 UTF-8，而中文 cmd 默认按 GBK 解析**，中文注释的 UTF-8 字节流在 GBK 下错位成对（lead+trail 吞掉后续 ASCII），行边界丢失、语法碎片化；
3. 试验「首行提前 chcp 65001」无效；改存 GBK 后经 `call` 传递仍碎裂（与测试管道叠加干扰）；
4. 另发现两个叠加 bug：`for /f ... in ('...')` 命令串内嵌 `sep='.'` 单引号破坏 for 定界；本机 `py` 启动器损坏（PEP-514 无注册，报 No installed Python found!），真机可用的是 `python` = `D:\app\Python\python.exe`。

**设计定稿**：放弃修补原脚本，按开发者指示重写为**纯 ASCII 极简启动脚本**——中文只允许出现在文件名，文件体禁用一切非 ASCII；Python 探测改为「先实测（`-c "import sys"`）再采用」的 py→python→python3 链。

**实施**（仅重写两个 bat，业务代码零改动）：

- `启动购物助手-网页版.bat`：探测链 → 启动 `web_server.py`（默认端口 8765）→ 失败时 pause + 指引日志位置
- `启动购物助手.bat`：同结构 → 启动 `shopping_agent.py`（透传 `%*`，`demo` 参数可用）
- `CLAUDE.md` 全局硬性规则新增「启动脚本编码红线」条目

**验证**：网页版经 GBK 中转真实调起——横幅、探测（自动落到 python）、服务启动全部正常，`GET /api/health` 返回 `{"ok": true}`，测毕已停服务；CLI 版与网页版同构，未做交互端到端（避免挂起），`demo` 回归待开发者双击自测。测试残留（临时 relay/副本/测试服务器）已全部清理。

**涉及文件**：`启动购物助手.bat`、`启动购物助手-网页版.bat`、`CLAUDE.md`、本文档。

## 抓取被拦截问题修复（问题疑惑区第1轮，web_scraper）

> 创建于 2026-09-12 00:41

**需求来源**：`docs/project/问题疑惑区.md` 待完成问题——天猫链接抓取 `Page.goto` 30s 超时（截图 `resource/网络抓取异常.png`）；开发者同时询问能否用 MCP/云端浏览器工具（如 Tavily）解决。

**方案商讨**：给出 A（修现有 Playwright 链路）/ B（CDP 接管本机已登录 Chrome）/ C（云端 API，不推荐：无登录态、机房 IP、隐私外发）三案，开发者选定方案 A。

**诊断过程**：
1. modlens 读取截图：纯白页面，`domcontentloaded` 30s 无响应；
2. 代码核查（codegraph + Read）：UA 硬编码 Chrome/124 与捆绑 Chromium 版本不匹配；goto 单次尝试；超时落「抓取异常」而非「交还人工」；
3. 实测：真实 Chrome 打开京东/天猫/淘宝首页全部正常 → 网络与指纹无问题；**原链接为直通车广告追踪链接（`ali_refid/ali_trackid/xxc=ad_ztc`），有时效与用户绑定，过期后即网络层黑洞**——结论：换任何工具都抓不到失效链接，问题主因是链接失效 + 旧链路对真实拦截无兜底。

**实施**（仅改 `web_scraper.py`）：
- 新增 `_find_system_browser()`：探测本机 Chrome/Edge，`_launch_browser` 优先 `channel` 启动真实浏览器（UA 不再覆盖、跟随真实浏览器），channel 启动失败回退捆绑 Chromium；`_check_browser_binaries` 同步接受系统浏览器；
- 新增 `_goto_with_retry()`：`domcontentloaded` 30s → `commit` 45s 两段式重试；
- 新增 `_save_failure_screenshot()`：失败截图存 `temp/`（已在 .gitignore）；goto 超时与验证码同样「交还人工」（block_reason 含「继续抓取」触发续跑、need_human=True 停止后续链接），与 `shopping_agent._flow_grab_and_compare` 的续跑契约对齐。

**验证**：模块导入自测通过；本机检测到真实 Chrome；真实 Chrome 启动 + 京东首页加载冒烟通过；用原始失效链接实测——两段式重试均超时后正确输出「交还人工」提示并留存截图（`temp/scrape_fail_20260912_003912.png`），续跑契约生效。

**遗留**：开发者需用**新鲜**商品链接做最终验收；若新鲜链接仍被拦截，升级方案 B（CDP 接管）。
