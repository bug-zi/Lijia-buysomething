## 问题疑惑区第10轮：负向约束失守 + 对话式调整失灵

> 创建于 2026-09-16 01:46

**背景**：问题疑惑区两项待完成——① 输入「买一双跑鞋，日常运动穿，透气轻便的，42码，不要黑色。预算300以内」，推荐的第一双就是黑色的（排除项被无视）；② 推荐后输入「第一款不要黑色的，换粉色+白色的，预算升到800」，AI 完全忽略追加要求，输出毫不相干的三个商品。

**根因（离线复现实锤）**：

- **真实搜索链路从不过滤**：`_flow_recommend` 走 `search_real` 时只传关键词，`require_tags`/`exclude_tags`/预算区间只在演示模式的 `mock_search` 里生效——「不要黑色」解析得再对，执行端也不看。
- **调整消息关键词被垃圾顶掉**：规则引擎对「第一款不要黑色的，换粉色+白色的，预算升到800」提取出的关键词是 `粉色+白色 预算升到8`（数字剥离把「800」啃成「8」、「预算升到」整体残留、「+」未清理），而合并逻辑 `delta.keyword or base.keyword` 让这份垃圾顶掉了上一轮的「跑鞋」→ 搜出毫不相干的结果。
- **「42码」被啃成「2码」**：数字剥离规则把尺码拆残，混进搜索词；且 `ShoppingRequest` 根本没有尺码字段。
- **LLM 脑补的次要污染**：调整类输入下 LLM 会结合历史脑补合并 query（如「粉色白色透气跑鞋」），`_is_redundant` 又因颜色词出现在 query 里而把「粉色/白色」标签误删成冗余（本轮修出）。

**落地**（`core/request_parser.py` + `shopping_agent.py` + `core/ai_client.py`）：

1. **硬过滤层 `_apply_hard_filters`**（核心）：真实搜索结果落地后真正执行——排除词子串命中剔除、预算硬界（超上限/低于下限）剔除、要求颜色按 **OR 语义**（「粉色+白色」命中任一即可；商品标注了颜色但全不符才剔；未标注颜色的保留并计数附注「请以详情页为准」）。全被过滤 → 如实输出去向统计（「排除词命中 X 款、超预算 Y 款」），声明不拿违规商品凑数，绝不展示违规结果。回复附剔除统计与颜色未标注提醒。
2. **调整合并关键词保护**：`_merge_request` 不再无脑 `delta.keyword or base.keyword`——delta 关键词先剥颜色词，再过「干净词校验」（≤12 字、无数字/+/预算噪声），不合格即拒收沿用上一轮关键词；「换成长裙」这类干净的新品类词正常放行。
3. **尺码体系**：`ShoppingRequest` 新增 `size` 字段；规则提取「42码/码数42/鞋码：42.5」（15~60 合理域）并整段从文本剥离（先于数字剥离，杜绝「2码」残片）；并入搜索词（如「跑鞋 42码」）+ 附注「卡片无尺码数据，以详情页为准」；`summary()` 显示；LLM schema 新增 size；会话态导出/恢复兼容（旧存档缺字段自动为空）。
4. **关键词卫生**：`_extract_keyword` 修复「预算升到800→预算升到8」「预算300以内→以内」残留（预算表达式连修饰词整体移除）；颜色词不进搜索词（由硬过滤层执行，多颜色也拼不进单一搜索词）；「换成/改成/调成/还是/仍是」等残片词入清理表（长词先于短词剥，防「换」先剥剩「成长裙」）。
5. **LLM schema 调整**：query 允许 null 并明示「只调条件没换品类时必须填 null，严禁脑补合并新品类词」；`_is_redundant` 对颜色词豁免（颜色是过滤材料不是冗余）。

**附带修复（测试卫生）**：`temp/test_buy_rank_intent.py` 此前把「张三/budget_max=500」写进项目根 `user_profile.json` 并遗留至今，导致 `test_dims_clarify.py` 判「预算不缺」而挂——两个测试均已改挂临时数据目录（`shopping_agent.data_dir` 指向 mkdtemp），互不污染。**注意**：根目录 `user_profile.json` 里现存的测试残留数据（张三/预算500/北京测试路）未动，请开发者确认是否需要清理（多账户机制下真实数据在 `accounts/<用户名>/`，此文件影响根账户的默认预算与订单预填）。

## 新账户引导修复（服务端标记）+ 账户数据 GitHub 隔离补漏

> 创建于 2026-09-16 00:22

**背景**：开发者实测多账户机制（注册「张三」新账户）后反馈两问题：① 新账户进入没有弹新手引导；② 配置库里常用购物平台登录信息仍在（同机共享是否正常？换电脑/同伴 clone 代码后是否会看到）。另确认一个关键问题：代码上传 GitHub、同伴 clone 到自己电脑后登录「bug子」账户，能看到本机的使用记录和平台登录配置吗？

**根因排查**：

1. **新账户无引导 = 真 bug**。引导标记 `sa_onboarded` 存在浏览器 localStorage（浏览器级、不分账户）；「退出登录」只清 token 不清引导标记，`onAuthed` 里换账户清理逻辑又因 `sa_username` 已被清空而短路跳过——同浏览器新注册的账户继承了上个账户「已引导」状态。
2. **平台登录信息同机共享 = 设计如此**。`login_state.json`（扫码登录态）与 `.browser_profile/`（浏览器配置文件）是**机器级**数据，按多账户设计明确保持全局共享（抓取用登录态与账户体系无关）。换新电脑天然不存在。
3. **GitHub 隔离有漏网**。核对 `.gitignore`：8 类按账户隔离的数据文件中 7 类已被既有规则覆盖（gitignore 无斜杠模式匹配任意层级，`accounts/<用户名>/` 下的同名文件同样被忽略），但 **`shopping_list.json` 漏配**（会连购物清单一起上传）；**`accounts.json`（账户表：用户名/邮箱/加盐密码哈希/持久登录 token）也未忽略**——token 上传等同把有效登录凭据放进仓库。

**落地**：

- **`index.html`**：
  - `doLogout()` 退出时补清本账户本地缓存（`sa_active_session`/`sa_uc`/`sa_onboarded`）并 `setSaToken("","")`；
  - 「已引导」升级为**按账户存服务端**：`markOnboarded()` 双写（localStorage 兜底 + `POST /api/usercenter {onboarded:true}`）；`onboardNext` 完成态与 `onboardSkip` 均改走 `markOnboarded()`；
  - `maybeOnboard()` 改为先 `loadUserCenter()` 再判断——服务端 `_uc.onboarded` 为真或本地标记存在则不弹，否则弹引导；`bootAfterAuth` 里原独立的 `loadUserCenter()` 并入 `maybeOnboard`（消除双请求）。
- **`core/user_center.py`**：`DEFAULTS`/`load()` 增加 `onboarded` 布尔键（缺省 False，旧数据自动补全）；`save()` 白名单新增 `onboarded`（仅接受严格 `True`）。
- **`.gitignore`**：补 `shopping_list.json`、`accounts.json`、`accounts/` 三行——账户数据（含账户表）从此不随仓库走，每台电脑各自注册、各自隔离。

**验证**（8902 临时服务 + 临时数据根，不碰真实数据与 8765）：

## 偏好档案空值保存失效修复 + 未保存修改弹窗（切页/退出/关闭）

> 创建于 2026-09-16 01:10

**背景**：开发者报两问题：① 用户中心-个人购物偏好档案里把有值字段（如肤质「一般」）清空后点保存，字段又变回旧值；② 希望有未保存修改时，切换页面/退出登录/关闭应用前弹窗提示，给「修改」「放弃」两个快捷操作。

**根因（问题①）**：空值被**前后端双重过滤**——前端 `saveProfile()` 收集表单时 `if (i.value && i.value.trim())` 把空输入直接丢出 payload；后端 `ProfileManager.update_batch()` 又用 `if v:` 跳过空串。于是「清空+保存」等效于「该字段未提交」，旧值原样保留。

**落地**：

- **`core/profile_module.py`**：`update_batch()` 空字符串语义化为**清空**——trim 后为空且档案中存在该字段则删除键并在报告标注「（已清空）」；非空更新照旧。内部两调用点核查安全：`continue_collect` 落档前已过滤空值；聊天「修改」指令传空值旧版本就被静默吞掉，现在语义化为清空（如「修改身高=」会清空身高并如实回报）。
- **`index.html`**：
  - `saveProfile()` 改为**全量提交**（空值 trim 后照进 payload），配合后端完成清空；
  - 新增档案脏检测：`loadProfile()` 渲染后 `snapshotProfileBaseline()` 记基线，`isProfileDirty()` 逐项比对当前值与基线（trim 后比较，输入后又改回不算脏）；保存成功/清空档案/向导落档后都会重载表单自动刷新基线；
  - 新增 `confirmDiscardProfile()` 主题化弹窗（复用 `_openConfirmBox`）：「未保存的修改」+「修改」（留在本页）/「放弃」（丢弃并继续）两键，放弃为红色危险样式；
  - 拦截三处：`switchTab()` 离开档案页签前询问（原函数体移入 `_switchTab()`；回档案页签且脏时**不重载表单**保护现场）；`doLogout()` 退出登录前询问；`window.beforeunload` 关闭应用/刷新前弹浏览器原生确认（浏览器安全限制：仅原生「离开/留下」样式，无法自定义「修改/放弃」按钮）。

**验证**：

- `temp/test_profile_empty_save.py` 离线断言 **15 项全过**（复现原 bug 路径清空后真删除且落盘不复活；混合批次一改一清一无关；全清空回空白 + is_empty 恢复；空档案存全空表单不报错；聊天修改指令回归含空值语义化；建档向导命名式只写非空值、连续跳过不误清）。
- 前端内联脚本（2 块，85KB）`node --check` 通过。
- `py_compile core/profile_module.py` 通过。

**真机冒烟清单（需重启 8765 服务后由开发者执行）**：

1. 肤质填「一般」保存 → 清空 → 保存：气泡报告应含「肤质(可选)=（已清空）」，重新进入档案页该栏为空；
2. 档案改一项不保存 → 点左侧其他页签：应弹「未保存的修改」，点「修改」留在本页、修改还在；再切、点「放弃」→ 正常离开，回来是已保存的旧数据；
3. 改一项不保存 → 点右上角退出登录：同样弹窗拦截；
4. 改一项不保存 → 关闭/刷新浏览器标签页：弹浏览器原生确认；
5. 回归：正常保存、清空全部档案、建档向导「跳过」均无弹窗误拦。

**注意（需开发者操作）**：与上节引导修复同批——8765 服务需重启后生效；重启前先 `netstat -ano | findstr :8765` 确认旧进程退出，避免假重启。

### 二次修正：留白实践 + 遮罩不再拦截（开发者复测反馈）

> 创建于 2026-09-16 01:50（追加）

**反馈**：光有手把手不够——用户操作留白缺失：介绍主题色/字体时想按自己喜好切换也不行，全程只能点「下一步」。

**根因**：① `#ob-blocker` 轻遮罩拦截了真实鼠标点击——侧栏（`backdrop-filter` 玻璃化）与卡片形成层叠上下文，聚光元素的 `z-index:1001` 升不出祖先上下文，命中测试被遮罩吃掉；此前自测用 JS `.click()` 绕过了命中测试，未暴露。② 体验型小步命中首个操作即自动跳下一小步，用户没机会自由把玩。

**修正**（`index.html`）：

- 遮罩改纯视觉聚焦：`#ob-blocker { pointer-events:none }`，调淡至 rgba .14——无论层叠上下文如何都不再拦截任何点击，用户在引导期间可自由操作界面任意处；
- 小步分两类：**实践型（stay）**——偏好卡、档案、Key、登录态、清单添加；命中操作后只就地确认（浮卡文案换「做得好，已经生效 + 可以继续随便玩…」+ toast），**不跳步**，用户玩够了自己点「下一步」；**推进型**——导航类小步与对话购物的发送/回复/买第X款链路保持自动前进（寻路性质，留白无意义）；
- 引擎：`runObPhase` 进入小步重置 `__acked`，`obNotify` 命中 stay 型走 `obAckPhase`（文案+toast，幂等不重复弹）。

**验证**（真机复测，一次性账户 `ob_stay_demo`，全程真实命中路径）：`elementFromPoint` 断言聚光导航/肤色点命中直达元素（修正前必为遮罩）；点主题色→浮卡换「做得好，已经生效」+toast、**步不推进**；连点字号/再换肤色→仍留原地不重复弹确认；浮卡「下一步」才前进；档案步「分批引导录入」、清单步「添加」同样确认留白；对话购物发送→等待→回复→买第1款→下单说明照旧自动推进；完成引导收尾、控制台零报错；`node --check` 通过；测试账户经注销端点清除、accounts 仅剩真实账户。

## 消息撤回后台照搜不误：协作式取消检查点修复

> 创建于 2026-09-16 02:50

**背景**：开发者报 bug——用户撤回已发送消息后，前端撤回与 AI 停回都正常，但后台的商品查询收不到「已撤回」，照样对撤回消息里的商品发起真实搜索。

**根因**：`/api/chat_cancel` 只登记取消标志（`_CANCEL_FLAGS`），而 `/api/chat` 把 `cs.chat(msg)` **整轮同步跑完后**才 `_consume_cancel` 检查标志——搜索期间全链路零检查点，浏览器照旧抓完两个平台（数十秒），结果才被丢弃。副作用：期间一直占着全局 `_BROWSER_LOCK`，撤回后紧接着发的新搜索要排队等废弃抓取跑完。

**方案**：协作式取消（Playwright 同步 API 无法从外部强杀，改为各耗时环节轮询取消信号提前收尾）——`cancel_check` 沿「web_server → ChatSession → ProductSearcher → web_scraper」四层下传：

- **`web_server.py`**：新增 `_CANCEL_EVENTS`（request_id → threading.Event）与 `_register_cancel_event()`；`/api/chat_cancel` 同步置标志+事件；`_api_chat`/`_api_image_post` 在拿锁**之前**注册事件（排队等待期撤回也能即刻生效），并把 `cancel_ev.is_set` 作为 `cancel_check` 传入 chat；请求收口处消费标志并清理事件。撤回先到、注册后到的竞态由注册函数兜底（发现标志已登记即置位事件）。
- **`shopping_agent.py`**：`chat()`/`chat_with_images()` 入口挂 `self._cancel_check`（finally 清理）；`_flow_recommend` 搜索前+搜索后双检查、`_flow_grab_and_compare` 抓取前+抓取后双检查，命中即返回「（消息已撤回，本次搜索已中止）」话术（正常会被 web 层丢弃，仅作不一致兜底），且不再写 `_pending_urls` 等会话态。
- **`core/product_searcher.py`**：`search_real` 平台间检查（撤回即不抓下一平台）；`grab_from_urls` 链接间检查。
- **`core/web_scraper.py`**：`search_platform` 入口检查（撤回则不启动浏览器）+ 卡片提取循环检查；`_goto_login_and_wait` 等扫码轮询循环检查（撤回后不再原地等满 3 分钟）。

**取消时效上界**：检查点粒度内最坏多抓「一张卡片的字段提取 / 一个详情页 / 一轮 goto」，无整平台或整轮浪费。

**验证**：

- TDD：新增 `temp/test_cancel_scrape.py` 先红后绿，7 项断言全过（假抓取不进真实浏览器）：search_real 平台间中止；search_platform 入口已取消不启浏览器；grab_from_urls 链接间中止；_flow_recommend 撤回前不发起搜索/撤回后不继续推荐；_goto_login_and_wait 撤回即停（<5s，不等 180s）；web_server 竞态兜底。
- 回归：temp 全部 15 个既有测试通过（其中 3 个假搜索器签名与新接口不一致致挂，已同步补 `cancel_check=None` 形参）；`py_compile` 四个改动文件通过；web_server 模块级导入经测试覆盖无启动错误。

**真机冒烟清单（需重启 8765 服务）**：发送一条会触发真实搜索的需求（如「跑鞋」）→ 搜索进行中点「取消并退回编辑」→ 弹出的浏览器应在数秒内停止抓取收尾；随后立刻重发新需求 → 不应长时间排队。撤回时机覆盖：浏览器刚弹出时、抓取中途、（若遇登录墙）等扫码期间。

## 修复：发送消息后切走窗口再切回，自己刚发的内容看不见（平滑滚底动画被后台丢弃）

> 创建于 2026-09-16 16:44

**背景**：开发者报 bug——发送消息后立刻切换窗口再切回来，有时看不到刚才输入的气泡；直到 AI 回复到达才连同自己的消息一起显示出来。

**根因（真机实验坐实）**：用户气泡本身是同步入 DOM 的（`sendMsg` → `appendMsg`），消息从没丢——丢的是**滚动**。append 后的滚底走 `scrollTo({behavior:"smooth"})` 平滑滚动动画，发送后立刻切走窗口时页面转入后台/被遮挡，浏览器渲染管线暂停，**进行中的平滑动画被整段丢弃**且不会恢复，视口停在原位，气泡留在屏幕下方看不见；AI 回复到达时 `appendMsg` 再次滚底，此时页面可见、动画正常执行，两条消息一起滚入视野——与症状完全吻合。「有时」= 只有切换发生在动画窗口期内才触发。实验另抓出一个放大因素：`#chat-messages` 的 CSS `scroll-behavior: smooth` 会让**直接赋值 `scrollTop` 也变成平滑动画**（实测 0ms 与 700ms 后均纹丝不动），而 `behavior:"instant"` 才能真正瞬时到位（0ms 即到底）。

**落地**（`index.html` 仅 `scrollChat()` 一处，纯前端）：页面隐藏（`document.hidden`）时改用 `behavior:"instant"` 直接跳底（无动画即无可丢弃）；可见时保持平滑滚动，但 550ms 后复核一次——未到位（动画被丢弃）则 `instant` 补跳（计时器在后台被节流，切回后立即生效，AI 未回也能先看到自己的消息）。顺带修正既有缺陷：历史恢复的 `behavior:"auto"` 会 defer 到 CSS smooth，`instant=true` 的「瞬时跳底」实际一直在做平滑滑动，现在真正瞬时（会话切换不再滑一下）。

**验证**（Chrome 真机 8765，`#chat-messages` 内 30 条填充消息可控复现）：

- 故障场景模拟（吞掉 smooth 调用=动画被丢弃）：修复后视口先停在 1242px 外（复现原 bug 状态）→ 550ms 兜底补跳生效回到底部；
- `document.hidden` 置真：`scrollChat` 瞬时跳底同步生效（off≈1.1px）；恢复后 `document.hidden` 正常还原；
- `instant=true` 历史恢复路径：真瞬时（修复前会被 CSS smooth 拖成动画）；
- 黄金路径回归：桩替 `api` 走完整 `sendMsg`——输入清空、用户气泡文本正确、AI 回复追加、打字动画与取消行清理干净、视口在底部，全部通过；全程未进真实搜索链路（后端零改动，8765 无需重启，刷新页面即生效）。
