# 2026-09-12 对话记忆 + 自由问答链路 — 设计文档（spec）

> 创建于 2026-09-12 23:44 ｜ 状态：已经开发者确认设计方向（方案1 末端兜底 + 解析历史注入）
> 来源：问题疑惑区「系统级prompt限制过硬」条目 T2 修复后复测定位——条数解析已生效（实测 top_n=5 正确），
> 真正痛点为 **AI 只有单轮对话记忆，持续交互能力欠缺**。

## 1. 背景与问题本质

- 会话框架已有：每会话独立 ChatSession 实例 + 7 个会话态字段落盘（web_server.py `_chat()`），消息全量存 chat_sessions.json 但**仅用于前端展示**。
- 断层：三处 LLM 调用全部无状态单轮——
  | 调用点 | 能看到 | 看不到 |
  |---|---|---|
  | 需求解析 ai_client.py `parse_shopping_request_with_llm` | 当前输入+档案+上一轮结构化需求(仅字段) | 历史对话 |
  | 推荐润色 `polish_recommendation_with_llm` | 本轮推荐列表+档案 | 追问与偏好变化 |
  | 自由问答 | —— | **该链路不存在** |
- 表现：系统是「命令路由器」（买第X款/换更修身的/预算升到300 可接），「第2款和第4款哪个更耐穿？」「刚才推荐里有没有百元内的？」等基于上下文的自由追问接不住，被当新需求瞎搜或触发品类追问。
- 附带死板点：LLM 解析 schema 无 top_n/per_platform_n 字段，条数解析完全依赖正则；润色 prompt 写死 TOP3/500字（本轮仅修 schema，润色 prompt 顺带动态化）。

## 2. 目标与非目标

**目标**
1. 需求解析注入最近对话窗口：接住「再要2个」「换成京东的」等口语化增量。
2. 新增自由问答链路：基于会话材料（历史窗口+上次推荐+档案）答疑，LLM 自判可答性。
3. LLM 解析 schema 增加 top_n/per_platform_n（规则优先，LLM 仅兜底规则漏掉的表述）。
4. 润色 prompt 的「TOP3/500字」写死改为按实际条数动态生成。

**非目标（本轮不做）**
- intent 字段前置路由（方案2，后续单独立项）
- 跨会话长期记忆/用户画像学习
- 流式输出、多模态上下文

## 3. 方案选型（已确认）

**方案1：末端兜底 + LLM 自判可答**。在 chat() 路由末端（解析不出明确需求时）尝试问答，一次 LLM 调用同时完成「可答性判断 + 回答」；不动现有路由优先级，零回归面。疑问句规则信号不单独做路由（简化：走到泛词兜底本身即信号）。

## 4. 详细设计

### 4.1 对话窗口（会话态 7→8 字段）

- `ChatSession` 新增 `_history: List[Dict[str,str]]`，元素 `{"role": "user"|"ai", "text": str}`。
- 维护：`chat()` 入口 push 用户消息；返回回复前 push AI 回复。窗口上限 `HISTORY_MAX_MSGS = 8`（4 轮），超出丢弃最旧。
- 进 prompt 时单条截断 ≤100 字（截断加「…」）。
- 持久化：`export_state()` 增加 `"history"` 键；`restore_state()` 读取，旧存档无此键 → 空列表（向后兼容）。web_server.py 无需改动。

### 4.2 需求解析增强

- `parse_shopping_request_with_llm(user_text, profile, prev, history=None)`：
  - user_prompt 新增「[最近对话]」块：按序每行 `用户：…` / `助手：…`（截断文本）；history 为空则省略该块。
  - sys_prompt 补充：「结合最近对话理解指代与增量表达（如『再要2个』『换成京东的』『第二种呢』）；条数要求输出到 top_n/per_platform_n」。
  - schema 新增：`top_n: number|null`（最终输出条数）、`per_platform_n: number|null`（每平台候选条数）。
- `RequestParser.parse(text, *, profile, previous, history=None)` 透传 history；`_merge_llm_json` 新增合并：**仅当规则解析结果为 None 时**采纳 LLM 的 top_n/per_platform_n（clamp 1..10），规则已解析到则不覆盖（规则优先红线）。
- 「再要2个」语义：交由 LLM 结合历史自然理解输出 top_n + is_adjustment，走现有 `_merge_request` 增量机制，不做特殊编码。

### 4.3 自由问答链路（核心）

**触发条件**（chat() 4.2 增量合并之后、4.3 泛词兜底之前插入，记 4.2.5）：
- 触发输入二选一：① 疑问信号——短句（≤40字）含疑问标记（？/?/为什么/哪个/哪些/怎么/怎么样/好不好/值不值/划算/值得吗/多少/有没有/能不能/可不可以/区别/差别/对比/理由/合适吗/好吗/行吗）；② 模糊输入——keyword 为空/泛词（其他/东西/商品/物品）且无品类/要求/用途（即原 4.3 junk 判定，计算逻辑上移复用）。
  > 设疑点：「第2款和第4款哪个更耐穿」会被规则提取出伪关键词「耐穿」直达搜索，故必须有疑问信号条件、且插入点须在搜索之前。
- 材料在：`self.recommender._last_products` 非空 **或** `self._history` 非空
- LLM 可用：`ai_client.get_config()["enabled"]` 为真
- 满足 → 调 `_try_free_qa(text)`；返回回答文本则直接展示；返回 None（含 NEED_SEARCH / 调用失败）→ 落回原 4.3/4.4 流程（品类澄清或搜索，行为与现状一致）。
- 不满足 → 直接原流程（与现状完全一致）；有明确关键词/品类的需求输入不触发（不加 LLM 时延）。

**新 LLM 能力** `answer_free_question_with_llm(question, materials: Dict) -> Optional[str]`（ai_client.py 第 4 个高层能力）：
- materials 由 agent 层组包：
  - `last_recommendation`：recommender 新方法 `last_recommendation_brief()` 输出紧凑列表——每条 {序号, 名称, 平台, 店铺, 到手价, 总分, 核心优点1条, 风险1条, 链接}；无则省略。
  - `recent_chat`：_history 截断文本。
  - `profile_brief`：档案摘要，**强制剔除**姓名/电话/地址/收货人等隐私字段（白名单取：身高/体重/预算/偏好类/风格类等购物相关字段）。
- sys_prompt 要点：
  1. 角色：购物助手，只基于【材料】回答用户问题；
  2. 红线：材料里没有的事实（历史价格/库存/真伪/其他商品）如实回答「材料中没有，无法判断」，**绝不编造**商品、价格、评价；
  3. 「买哪个好」类问题：基于评分材料给建议并说理由，结尾带一句下单前核对提醒；
  4. 输出约定：若问题是要求搜索新商品/与材料完全无关 → 仅输出一行 `NEED_SEARCH`；否则输出 Markdown 回答（≤300 字）。
- 调用参数：temperature=0.4、max_tokens=500、timeout=10（与 polish 同级）；失败返回 None。

**回退矩阵**（全链路规则兜底红线）：

| 情况 | 行为 |
|---|---|
| LLM 未配置 / 调用失败 / 返回 None | 原 `_start_clarify` 品类澄清 |
| LLM 返回 NEED_SEARCH | 同上 |
| 材料为空 | 不进问答链路，直接原行为 |
| 正常回答 | 展示回答文本 |

### 4.4 润色 prompt 动态化（顺带）

- `polish_recommendation_with_llm` 的 sys_prompt 中「TOP3」「不超过500字」改为动态生成：字数上限 = 500（≤5款）/ 每多 1 款 +100 字（封顶 1000），标签「[TOP{N} 推荐列表]」随实际条数。

## 6. 测试点（模块自测，不进真实搜索链路）

1. 解析回归：原话「上淘宝和京东各筛选出最合适的前4名商品…最终给我排名前5的商品」→ top_n=5、per_platform_n=4 不回归。
2. 历史注入：构造 _history 后「再要2个」→ LLM 输出 top_n=2 + is_adjustment=true（有 key 时手测；无 key 时确认静默回退规则解析）。
3. 规则优先：规则已解析出 top_n 时，LLM 给不同值不覆盖。
4. 问答触发：「第2款和第4款哪个更耐穿」+ _last_products 有数据 + 有 key → 走问答返回回答；无 key / 无材料 → 回退品类澄清。
5. NEED_SEARCH：「帮我找点便宜的」之类解析不出品类、语义实为新搜索的输入，在 4.3 命中问答时 → LLM 返回 NEED_SEARCH → 回退品类澄清而非硬答。
6. 持久化：export_state/restore_state 含 history 往返一致；旧 chat_sessions.json（无 history 键）加载不报错。
7. 隐私：材料组包结果不含姓名/电话/地址（打印 materials 断言）。

## 7. 边界与风险（如实声明）

- 含明确品类词的追问（「有没有百元内的连衣裙」）会被正常解析为新需求走搜索，不进问答——本轮不做意图分类，接受此边界，后续 intent 立项再收。
- 弱模型可能偶发把可搜需求误答：以 NEED_SEARCH 约定 + 材料为空不触发双保险兜住，误答内容仍限定在材料范围内、不会编造商品。
- _history 明文随 chat_sessions.json 落盘（与现有消息持久化同级，无新增敏感面）。
