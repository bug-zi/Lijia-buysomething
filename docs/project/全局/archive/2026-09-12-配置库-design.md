# 配置库：API Key + 网站登录态管理（spec）

> 创建于 2026-09-12 02:26（开发者优化建议发起，AI 起草）
> 状态：已实施（2026-09-12 自测/demo 回归/接口冒烟/京东「检测→清除→再检测」真实冒烟通过；扫码登录 E2E 与抓取顺带回写由开发者验收）
> 来源：`docs/project/优化建议区.md` 2026-09-12 轮次——「配置网站 cookie 缓存信息能不能直接进配置库（API Key 配置模块升级成配置库，常用网站登录也在这里完成）；登录信息一般多久过期，有没有不过期的方法（比如说配置 cookie）」

## 背景与决策

- 现状：API Key 配置为前端 Tab 5「API Key 设置」+ 后端 `/api/apikey`（set/test/clear），存 `api_key.json`，脱敏展示——**工作正常，本期不动**。
- 登录态现状：抓取已用 `launch_persistent_context` + 固定 `.browser_profile` 持久化配置目录，**Cookie 本体已在本地持久化**（服务重启不丢，登录一次短期免重复扫码）；登录墙时弹有头浏览器人工扫码（`_goto_login_and_wait`，最长等 180s）。缺的只是**可见性与管理入口**——本 spec 补齐的就是这块。
- 平台范围：仅**京东、淘宝/天猫**（`SEARCH_SITES` 实际支持的两个平台；拼多多不在其中，如实不纳入）。同日既有 spec 已实测：京东/淘宝搜索**均强登录**，登录态管理为抓取刚需。
- 方案选型（三选一，开发者已定）：**方案 A——独立 `config_store.py` 模块**。已否决：方案 B（全部塞进 web_scraper/web_server，职责混杂、文件继续膨胀）、方案 C（Cookie 导出/导入，与持久化 profile 重复，且复制会话凭据易触发风控、触碰「绝不过手账号密码」红线精神）。
- 检测方式（开发者已定）：**缓存 + 手动检测**。配置库展示缓存状态（随抓取/登录自动更新），另提供「立即检测」按钮按需触发；不在打开页面时自动弹浏览器（零打扰、降低风控暴露面）。

## 登录有效期解答（写入界面文案与日志）

登录信息存放在本项目 `.browser_profile` 浏览器配置目录中，重启不丢失。有效期各平台不一且不承诺固定值：一般几天到几个月（京东 PC 会话常见约 30 天，淘宝凭定期使用可维持更久）；改密码、异地登录、平台风控都可能随时提前失效。**没有真正永不过期的方法**——持久化保存 + 低频正常使用就是最接近的做法；失效后在配置库点「扫码登录」重新授权即可。不支持从别处导入 Cookie：复制会话凭据极易触发风控，且程序绝不过手账号凭据。

## 功能设计

### 1. 新模块 `config_store.py`

- `LOGIN_STATE_FILE = login_state.json`（项目根，与 `scrape_cache.json` 并列）；**只存状态与时间戳，绝不存任何 Cookie 内容**。结构：`{platform: {status, checked_at, source, note}}`，status ∈ `已登录/未登录/未检测/检测中/登录中/未知`。
- `get_states()`：读缓存，合并内存中运行任务的状态（`threading.Lock` 保护缓存文件与任务表）。
- `check_login(platform)`：有头浏览器（复用 `web_scraper._launch_browser`）短暂访问检测页，判定后写缓存并关浏览器，≤25s 超时。
- `start_manual_login(platform)`：后台线程执行 `_goto_login_and_wait`（复用 `LOGIN_URLS`），任务表记录 `登录中/成功/失败`；成功写 `已登录`，失败/超时保持原状态。
- `clear_login(platform)`：启动持久化 context，`clear_cookies` 按平台域名过滤（京东 `jd.com`；淘宝 `taobao.com` + `tmall.com`），状态置回「未检测」。
- `record_state(platform, status, source)`：供 `web_scraper` 抓取时顺带写入。

### 2. 平台检测方法（复用现有特征判定思路，不绕风控）

| 平台 | 检测页 | 判定 |
|---|---|---|
| 京东 | `order.jd.com/center/list.action` | 被 302 到 passport 域 = 未登录；留在 order 域 = 已登录 |
| 淘宝/天猫 | `www.taobao.com` | cookie `unb`（用户编号）存在**且**页面不含「亲，请登录」= 已登录；无 `unb` 或页面含「亲，请登录」= 未登录 |

具体特征以实现时实测为准，与现有 `_check_block` 特征词/URL 域名机制同思路。

### 3. 接口（`web_server.py` 新增）

- `GET /api/login` → `{ok, states: [{platform, status, checked_at, source, note}]}`。
- `POST /api/login` → `{action, platform}`：
  - `check`：同步执行（≤25s），完成后写缓存返回结果；
  - `login`：启动后台任务立即返回 `{running: true}`；前端每 3 秒轮询 `GET /api/login` 直到结束（HTTP 不阻塞、无超时风险）；
  - `clear`：同步执行，返回清理结果。
- `/api/apikey` 与 `ai_client.py` **一行不动**。

### 4. 前端（`index.html` Tab 5 升级为「配置库」）

- 上半区 **AI 能力**：现有 API Key 表单、按钮、状态卡原样保留，仅 Tab 名与标题改为「配置库」。
- 下半区 **网站登录态**：京东、淘宝/天猫各一张状态卡（状态徽标 + `checked_at` + 来源），按钮按状态流转：
  - `未检测` → [立即检测] [扫码登录]；
  - `已登录` → [重新检测] [清除登录态]；
  - `未登录` → [立即检测] [扫码登录]；
  - `登录中/检测中` → 按钮禁用 + 进行时提示。
- 底部固定「登录有效期说明」一段（见上文引文）。
- 侧栏入口文案 `🔑 API Key 设置` → 配置库（图标从 Google Fonts Icons 选配，遵循无 emoji 图标红线；本条仅改文字与图标，不改结构）。

### 5. web_scraper 顺带更新（最小侵入）

在 `search_platform` 既有登录墙判定处插入两处 `config_store.record_state` 调用：二轮重搜成功 → `已登录`（source=「抓取时」）；仍遇登录墙 → `未登录`。不改抓取主流程逻辑。

## 错误处理与红线

- Playwright 缺失 / 无浏览器 / 启动失败 → 如实返回原因文案，绝不编造状态（数据真实性红线）。
- 检测超时 → 记「未知（检测超时）」，不算登录也不算失败。
- profile 占用冲突 → 沿用 `_launch_browser` 三段重试；仍失败提示「抓取或登录正在进行，请稍后再试」。
- 并发：`config_store` 内 `threading.Lock` 保护缓存文件与任务表；login 任务同平台互斥。
- 红线：程序绝不过手账号密码（只弹窗等人工扫码）；不做 Cookie 导入导出；不绕任何风控；`login_state.json` 无敏感内容。

## 非目标（本期不做）

- 拼多多/抖音等更多平台；Cookie 导出/导入；自动定时检测（无轮询，克制条款）；
- AI Key 模块重构；前端整体结构改造；
- 多账号/多 profile 管理（单用户单 profile 不变）。

## 验收标准

1. 配置库 Tab 正常渲染：AI Key 区功能回归不变（set/test/clear 全通）；
2. 「立即检测」：未登录 → 正确判「未登录」；扫码登录后 → 正确判「已登录」；超时场景 → 「未知」；
3. 「扫码登录」：弹有头浏览器跳登录页，扫码成功自动写「已登录」，失败/关窗保持原状态且不阻塞页面（轮询正常结束）；
4. 「清除登录态」：按平台域清理后，再检测显示「未登录」；另一平台登录态不受影响；
5. 抓取顺带更新：触发一次登录墙→登录→「继续抓取」后，配置库状态自动变「已登录」；
6. `login_state.json` 全文无任何 Cookie/token 内容；
7. Playwright 缺失环境：接口如实报错不崩溃，其余功能（AI Key）不受影响。
