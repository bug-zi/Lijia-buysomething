# 项目概况

**项目名称**：全自动个人购物 AI 助手（ShoppingAgent，网页版 + 命令行版）

**项目定位**：一个运行在个人电脑本地的对话式购物决策 Agent。用户用自然语言提出购物需求（如「买一条夏天的连衣裙，预算200以内」），系统完成 **建档 → 需求解析 → 选品 → 评价分析 → TOP3 推荐 → 购物车/比价 → 下单模拟 → 物流跟踪 → 售后** 全流程辅助。

**核心特点**：

- **零第三方依赖启动**：后端基于 Python 标准库 `http.server`，前端为单文件 `index.html`，双击 `.bat` 即可运行；
- **AI 增强可选、全链路兜底**：LLM（智谱/DeepSeek/通义/硅基流动/豆包/Kimi，OpenAI 兼容协议）仅做增强，任何 AI 调用失败都自动回退到规则引擎，功能永不因 AI 失效而中断；
- **真实数据优先、绝不编造**：数据源三层回退（真实抓取缓存 → Playwright 真实浏览器抓取 → 演示 Mock），每条商品带 `data_source` 标注（📦 真实 / ⚠️ 演示）；
- **人机协作抓取**：受电商反爬限制，采用「用户粘贴 1-5 个商品详情链接 → Agent 逐个抓取打分」的协作模式，遇验证码暂停并交还用户手动处理（回复「继续抓取」续跑）；
- **支付安全红线**：系统只做下单流程模拟（生成订单号），**绝不代用户支付**，界面与回复中多处明示免责提醒。

**目标用户**：有跨平台比价、选品决策需求的个人消费者；同时作为「LLM 应用 + Agent 工作流」的教学/演示项目。

**当前状态**：可运行的单机完整版（dev 分支），已实现全部核心模块与网页 UI，真实抓取依赖本机安装 Playwright + Chromium。


# 项目样情

### 1. **业务知识与领域模型**

- **核心业务价值**：解决「跨平台购物决策信息分散、评价真假难辨、比价费时」的问题。目标用户为个人消费者。当前为单机个人项目，无 DAU/MAU 等运营指标；可衡量的过程指标包括：推荐采纳率（用户回复「买第X款」的比例）、真实抓取成功率、LLM 调用成功率（`ai_client` 内置 success/fails 计数）。
- **领域概念与模型**：

  | 领域概念 | 代码载体 | 存储（"表"） | 说明 |
  |---|---|---|---|
  | 用户偏好档案 UserProfile | `profile_module.ProfileManager`（约 27 个字段：身高/体重/尺码习惯/色系偏好与避雷/风格/材质/版型/收货人三要素/预算上限/优先因素/品牌偏好/是否接受杂牌与预售/发货地区/讨厌元素等） | `user_profile.json` | 推荐打分的永久参考依据 |
  | 结构化购物需求 ShoppingRequest | `request_parser.ShoppingRequest`（keyword/category/price_min-max/platforms/require_tags/exclude_tags/purpose/is_adjustment/target_rank/needs_clarify） | 内存（会话内） | 需求解析的输出、增量调整的合并对象 |
  | 商品 Product + 评价 Review | `product_searcher.Product/Review`（pid/平台/原价/到手价/优惠/销量/发货天数/店铺/售后政策/标签/好评差评点/好评率/`data_source`） | `scrape_cache.json`（真实，30 分钟 TTL）、`search_history.json`、代码内 `MOCK_CATALOG`（演示库：连衣裙/运动鞋/耳机/手机/T恤 五品类） | 跨平台统一结构，`_build_product` 做多来源字段别名兼容 |
  | 评分明细 ScoreBreakdown | `recommender.ScoreBreakdown`（五维 0-100 + 总分） | 内存 | 横向对比与推荐理由的依据 |
  | 购物车项 CartItem | `virtual_cart.CartItem`（name/platform/url/current_price/note/monitor/pid） | `virtual_cart.json` | Agent 内部收藏 + 降价监控，不等同平台官方购物车 |
  | 订单 Order + 物流事件 LogisticsEvent | `order_manager.Order/LogisticsEvent`（订单号/状态/商品/金额/收货人/运单号/事件轨迹） | `orders.json` | 下单模拟与物流推进 |
  | LLM 配置 LLMConfig | `ai_client.LLMConfig`（key/base_url/model/provider/success/fails） | `api_key.json` | Key 脱敏存储，绝不回传前端明文 |

- **关键业务流程**：

  **① 购物主流程**（`shopping_agent.ChatSession.chat` 意图分流）：
  自然语言输入 → 命令分流（档案/订单/购物车/取消/链接识别）→ 需求解析（规则正则 + LLM JSON 增强，失败静默回退；档案 `budget_max` 作默认预算）→ 输出搜索关键词并提示用户粘贴商品链接 → Playwright 逐个抓取详情页（遇验证码暂停交还人工）→ 预算初筛 → 五维打分排序 → 输出 TOP3（优点≥3/缺点≥2/价格分析/适配说明/风险提示/评分表/横向对比 + AI 导购点评）→ 用户「买第X款」→ 订单草稿预览 + 支付风险提醒 → 明确「确认」→ 模拟下单（订单号+运单号）→ 物流按时间推进（已下单→已发货→运输中→派送中→已签收，10 分钟内新单加速到 24h 演示）→ 售后/取消。

  **② 订单状态机**：`待支付 → 已支付 → 已发货 → 运输中 → 派送中 → 已签收`；分支状态：`售后处理中`（已发货后只能走售后不能取消）、`已取消`。

  **③ 档案录入流程**：`录入档案` → 19 个批次分步引导收集（同类语义字段同批，防多值错位；支持「跳过」与断点续录「继续建档」）→ 写入 `user_profile.json`；支持「查看档案/修改身高=175/清空XX」等快捷命令。

  **④ 图片多模态流程**：场景 A 单图找同款（视觉模型提取品类/颜色/风格/材质 → 输出搜索关键词）；场景 B 多图对比（Markdown 对比表 + 结合档案的选购建议）。均标注「图片分析仅为视觉推测，以商品网页为准」。

  **⑤ 五维评分模型**（`recommender.py`，加权总分 0-100）：档案匹配度 30%（色系/风格/材质/版型/尺码/品牌/杂牌/讨厌元素/发货地区）、性价比 25%（折扣率+销量+预算贴合）、真实口碑 20%（好评率+带图追评占比+评价量）、差评风险 15%（差评点数量与严重词命中）、发货时效 10%（天数+自营/次日达加成）；TOP3 内同平台尽量拉开。


### 2. **系统架构与物理部署**

- **技术栈**：
  - 后端：Python 3.9+，**纯标准库**（`http.server.ThreadingHTTPServer`、`urllib`、`json`、`dataclasses`、`threading`、`re`、`uuid`）；
  - 前端：原生 HTML/CSS/JS 单页 `index.html`（6 个 Tab：对话购物/偏好档案/我的订单/虚拟购物车/推荐结果/AI 设置，内置 Markdown 渲染）；
  - AI：OpenAI 兼容 `chat.completions` 协议，多服务商自动探测（智谱 bigmodel / DeepSeek / 通义千问 / 硅基流动 / 豆包火山方舟 / Kimi），视觉任务按服务商自动切换视觉模型（如 glm-4-flash → glm-4v-flash）；
  - 抓取（可选依赖）：Playwright + Chromium 有头真实浏览器（stealth JS 注入、持久化用户配置目录 `.browser_profile/` 复用登录态、0.8–2.2s 随机延迟、慢速滚动拟人化）；
  - 存储：本地 JSON 文件，无数据库；
  - 启动：`启动购物助手.bat`（CLI）/ `启动购物助手-网页版.bat`（Web，4 层 Python 解释器探测兜底，日志写 `%TEMP%\shopping_agent_web_error.log`）。

- **逻辑架构**（分层，自上而下）：

  ```
  表现层   index.html 单页（对话/档案/订单/购物车/推荐/AI设置）
  接口层   web_server.py：/api/health /api/chat /api/profile /api/orders
           /api/logistics/<oid> /api/aftersale /api/cancel /api/apikey
           /api/cart(POST/GET/DELETE) /api/scrape /api/image + 静态托管
  编排层   shopping_agent.ChatSession：意图分流、会话状态
           （上次请求/待确认订单/建档模式/被拦截URL）、工作流串联
  能力层   request_parser（需求解析）｜recommender（五维评分+TOP3）
           ｜product_searcher（三层回退搜索）｜virtual_cart（购物车+监控）
           ｜order_manager（下单模拟+物流）｜profile_module（档案）
  基础设施 ai_client（LLM/视觉，Key安全）｜web_scraper（Playwright抓取）｜JSON 持久化
  外部系统 LLM 服务商 API ｜ 淘宝/京东/拼多多/抖音商品页 ｜ 慢慢买比价 ｜ Trae Agent 桥接(/api/scrape)
  ```

- **物理部署**：**单机单进程部署**，服务绑定 `127.0.0.1:8765`，仅本机访问；`ThreadingHTTPServer` 多线程处理请求，全局 `SESSION` 单例（ChatSession）+ `SESSION_LOCK` 互斥锁保证会话状态一致。无集群、无分布式、无容器化；升级=替换文件重启 bat。
- **数据架构**：JSON 文件即数据库（见领域模型表），数据流向：用户输入/网页抓取 → 结构化 Product/Order → 内存会话 → 落盘 JSON；`scrape_cache.json` 带 30 分钟 TTL 过期；数据分析逻辑集中在 `recommender`（评分）与 `order_manager._advance_logistics`（虚拟时间物流推进，幂等）。

  - **下游**：本地前端（JSON over HTTP，CORS 全开放，仅本机）。项目为个人项目，无外部下游消费方；联系人即开发者本人。


### **4. 项目管理与评估维度**

- **进度与成本管理**：单人项目，无正式排期与预算体系。成本近乎为零：LLM 默认用免费档模型（glm-4-flash / glm-4v-flash）、本机部署无服务器费用、无付费数据源。迭代以「增强方案 → 改动清单 → 验证清单」的小步闭环推进（见 `.trae` 文档），git 单分支（dev）提交。
- **质量与风险管理**：
  - 质量：靠模块自测入口 + demo 全流程用例 + 验证清单人工回归；代码内多处防御式设计（JSON 读写容错、字段别名兼容、空值兜底）。
  - 主要风险与已有对策：
    - **反爬与合规风险**（最高）：电商反爬持续升级 → 已采用「用户粘贴单链接 + 真实有头浏览器 + 验证码交还人工 + 禁止批量遍历」的克制策略，将抓取行为控制在个人辅助范围内；
    - **数据真实性风险**：严禁编造 → `data_source` 强制标注，演示数据加 ⚠️ 声明；
    - **模型幻觉风险**：LLM 仅做解析/摘要/润色，不做事实决策；结构化 JSON 输出 + 规则校验合并 + 失败回退规则引擎；
    - **支付/资金风险**：硬性约束——不代支付，确认前后双风险提醒；
    - **隐私风险**：API Key 本地存储且脱敏展示（前后 4 位），档案/订单仅存本机；地址电话属敏感信息，当前明文存本地 JSON，是待改进点。
- **商业战略契合度**：作为个人工具与 AI Agent 教学演示，价值在于完整跑通「LLM + 规则混合编排、人机协作、全链路降级」的工程范式，具备演化为插件式购物助手或课程案例的潜力。


### **5. 市场环境与用户反馈**

- **市场调研与竞品分析**：
  - 电商内置 AI 导购（淘宝问问、京东京言）：优势是站内数据与交易闭环，劣势是仅限单平台；
  - 比价工具（慢慢买、什么值得买）：历史价/优惠信息强，但无个性化档案与对话式交互；
  - 通用大模型（ChatGPT/豆包等）：会话能力强，但拿不到实时真实价格评价，易编造；
  - **本项目差异化**：跨平台统一打分 + 个人持久档案驱动 + 「用户粘贴链接」的人机协作模式巧妙绕开批量反爬 + 数据真实/演示双标注的诚实原则 + 全流程闭环（含模拟下单与售后）。
- **用户反馈与体验**：当前用户即开发者本人与课程演示受众。产品内置的体验设计包括：信息不全时主动追问而非盲搜、增量调整（「第二款太宽松，换更修身的，预算升到300」可直接叠加修改）、演示模式让无网络/无 Key 环境也能看效果、验证码人机协作提示。已知痛点：真实抓取成功率受平台风控波动影响大；历史价格曲线暂不支持（仅当前价对比）。


### **6. 团队角色与沟通机制（特别是AI项目）**

- **团队角色重组**：本项目为 AI 时代的「单人全栈 + AI 结对」形态，实际承担了多类 AI 项目角色：
  - **提示词工程师**：`ai_client.py` 中 5 组 system prompt（需求解析 JSON 输出器/评价分析师/购物顾问/找同款/多图对比），全部约束「只输出合法 JSON」「不吹捧」「失败留空」；
  - **数据工程师**：抓取字段提取、多来源字段别名兼容（`_build_product`）、缓存 TTL 设计；
  - **爬虫/反风控工程师**：stealth 注入、持久化会话、拟人化随机延迟、验证码人机协作流程；
  - **规则工程师**：需求解析正则与词典、五维评分公式、请求合并冲突消解（如「宽松 vs 修身」冲突时排除优先）；
  - **AI 测试/运维**：demo 用例回归、验证清单、启动脚本 4 层兜底与错误日志。
- **实验驱动与预期管理**：需求模糊处以「演示模式（Mock 标注 ⚠️）+ 增强文档验证清单（8 条可执行验证步骤）」充当实验看板；架构决策（切平台回退、仅当前价比价、桥接注入）均以「用户已确认决策」形式显式记录，属于典型的假设—验证—固化迭代。预期管理体现为：明确告知用户「历史曲线不支持」「抓取被拦截」「图片分析仅为推测」，不夸大能力。
- **多维风险管控**：
  - 数据质量：真实/演示双标注、绝不编造、字段空值兜底；
  - 模型幻觉：LLM 不做决策只做增强、结构化输出 + 规则校验、7–10s 超时熔断；
  - 安全合规：Key 脱敏不回传、不代支付、单链接克制抓取、模拟下单免责声明；
  - 伦理：不绕过平台验证码（交还人工）、不批量爬取、尊重 robots 与登录墙。
