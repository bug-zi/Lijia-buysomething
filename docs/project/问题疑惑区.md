### 第11轮（260916）：用户中心「交互风格 × 界面字体」互斥（双进程数据互踩）

- [X]  有一个bug：用户中心 · 界面与行为偏好中的交互风格（人群）似乎与上面的界面字体存在互斥问题：比如我交互风格选择学生党的话，字体就被强制成默认黑体，无法修改，修改成宋体或者楷体的话，交互风格（人群）就变成默认了。请你修复这个bug

  **修复说明（2026-09-16）**：

  - **排查结论（应用代码无罪）**：偏好保存链路前后端逐环验证均正确——后端 `user_center.save()` 白名单逐键合并（模块自测含「部分更新不丢其他键」断言）、`/api/usercenter` 端点透传、前端 `setUcPref` 单键提交；用临时账户走真实 HTTP 与真机浏览器（Playwright）双向实测：选「学生党」再选「宋体/楷体」两设置并存、页面字体实际生效，复现不出互斥。
  - **根因（环境层）**：8765 端口**同时挂着两个 `web_server.py` 进程**（01:51 与 02:23 先后启动，后者为旧进程未退出的「假重启」——第 5 轮已记录过同款陷阱）。Windows 下 `SO_REUSEADDR` 允许双绑定，两个进程对同一份 `accounts/<用户名>/user_center.json` 各自「读-改-写」且互不知晓：A 进程写入「宋体」后，B 进程持旧快照写入「学生党」，把字体冲回默认——正是「选人群→字体回默认；改字体→人群回默认」的互斥观感。两个账户文件的受损状态（bug子 丢字体、李四 丢人群）均带典型丢更新签名。
  - **附带隐患**：`user_center._save_raw` 原为原地截断重写，并发/中断可留半截 JSON；`_load_raw` 读坏文件会静默当空数据处理并回写全默认——偏好存在整档莫名重置的连锁风险。
  - **落地**：① `web_server.py` 启动前**端口预检**（`_port_in_use`）——端口已有存活服务即打印中止横幅与 `netstat/taskkill` 处置命令、拒绝双启动，从源头杜绝双进程（对真机 8765 实测拦截生效）；② `core/user_center.py` 改**原子写**（临时文件 + `os.replace`），失败不破坏旧文件、不留 .tmp 残留。
  - **验证**：`temp/test_fix_prefs_mutex.py` 离线断言 4 项全过（修复前 2 项按预期失败：占用端口时 `run()` 确会双绑定挂起、写失败确实毁旧文件；修复后转绿；空闲端口不误判正常起服务）；`user_center.py` 模块自测（含迁移/部分更新）回归通过；`py_compile` 通过。
  - **开发者需做**：① 现存僵尸进程需清理一次——`netstat -ano | findstr :8765` 可见两个 LISTENING PID，杀掉其一（建议 `taskkill /F /PID <新启动那个的PID>`，旧进程正承载服务）后正常使用；此后守卫会在下次「假重启」时直接拦下并给出指引；② bug子/李四 账户的偏好已被竞态写坏，到用户中心重新设置一次即可（当前代码下单键保存不会互相覆盖）。

### 第10轮（260916）：负向约束失守 + 对话式调整失灵

- [X]  很大的一个问题：AI对话助手还是不能很好理解我输入的需求和指令：比如我输入“买一双跑鞋，日常运动穿，透气轻便的，42码，不要黑色。预算300以内”，AI助手给我推荐的第一双鞋子就是黑色的。请你看看如何避免这种问题的发生。
- [X]  当前对话的“对话式调整与追问”也是完全不行，比如我还是先在新会话中输入“买一双跑鞋，日常运动穿，透气轻便的，42码，。预算300以内”，AI助手推荐了三双鞋；然后我再输入“第一款不要黑色的，换粉色+白色的，预算升到800”——AI助手完全就忽略了之前的对话，不知道是我的追加要求，直接给我输出了毫不相干的三个东西。这个问题也很大

  **修复说明（2026-09-16）**：

  - **根因**：① 真实搜索链路从不过滤——`_flow_recommend` 只把关键词传给 `search_real`，`require_tags`/`exclude_tags`/预算区间只在演示模式生效，「不要黑色」解析得再对执行端也不看；② 调整消息被规则引擎提取出垃圾关键词（`粉色+白色 预算升到8`），合并逻辑 `delta.keyword or base.keyword` 让它顶掉上一轮的「跑鞋」→ 搜出毫不相干的结果；③「42码」被数字剥离啃成「2码」混进搜索词，且 `ShoppingRequest` 无尺码字段；④ LLM 对调整类输入会脑补合并 query，`_is_redundant` 还会把颜色标签误删成冗余。
  - **落地**（`core/request_parser.py` + `shopping_agent.py` + `core/ai_client.py`）：新增**硬过滤层 `_apply_hard_filters`**——真实搜索结果落地后真正执行排除词剔除、预算硬界剔除、要求颜色 OR 语义（「粉色+白色」命中任一即可，未标注颜色的保留并如实附注）；全被过滤时输出去向统计、绝不拿违规商品凑数。调整合并加**关键词保护**（delta 关键词剥颜色+干净词校验，不合格沿用上一轮关键词；「换成长裙」类新品类词正常放行）。新增**尺码体系**（size 字段：解析→并入搜索词→summary→LLM schema→会话态持久化，全链路「42码」不再变残片）。关键词卫生（预算表达式整体移除、颜色词不进搜索词、残片词清理表）。LLM schema 明示「只调条件没换品类时 query 填 null，严禁脑补」。
  - **验证**：`temp/test_hard_filters.py` 离线断言 7 项全过（可复跑）；`test_buy_rank_intent` / `test_review_honest` / `test_dims_clarify` / `test_food_clarify` / `test_profile_empty_save` 回归全过。附带修复测试卫生问题（buy_rank_intent 曾把测试档案写进真实 `user_profile.json`，已改临时目录）。已知边界与真机冒烟清单见 `docs/log/260916.md` 第10轮小节（需重启服务）。

- [X]  根据"2026-09-15-全功能演示操作手册.md"文档中的操作，我先在新会话中输入"买一双跑鞋，日常运动穿，透气轻便的，预算300以内"，AI助手正常搜索了三双鞋子给我；但是当我再次输入"买第2款"时，AI并没有按照预期的"订单草稿 + 支付风险提醒。"进行，而是又去给我搜索了三双鞋子并输出了新搜索得到的鞋子的信息。

  - **验证**：`temp/test_buy_rank_intent.py` 离线断言 4 项全过（含用会脑补的假 LLM 复现真机污染路径、零调用零搜索、正常需求与修正意见路径回归）；`test_review_honest` / `test_t4_parser` 回归全过。真机冒烟清单见 `docs/log/260915.md` 末节（需重启服务）。
