# 多账户机制 设计文档（spec）

- 日期：2026-09-15
- 状态：待开发者审阅
- 来源需求：`docs/project/新功能开发区.md` 待完成区「建立多账户机制（各个账号直接隔离）；创建账号时填写用户名+邮箱+密码即当作创建成功（当前只是在本地使用，并没有部署上线，所以就先这样简单实现）」
- 已确认决策：AI 配置（api_key.json）按账户隔离；电商平台登录态（login_state.json）保持全局共享；首个注册账户继承存量数据；采用「方案A：账户上下文 + 路径解析函数」。

## 1. 背景与目标

现状为单用户：`user_profile / orders / virtual_cart / shopping_list / chat_sessions / user_center / api_key / search_history` 均为项目根一份固定 JSON，模块硬编码路径；系统无任何用户账户体系（现有 `/api/login` 是电商平台抓取登录态，与用户账户无关）。

目标：
- 建立本地多账户机制：注册（用户名+邮箱+密码，填完即成功）、登录、退出。
- 各账户数据完全隔离；API Key 也按账户隔离。
- 本地单机简单实现，不引入数据库、不引入第三方认证库，纯 Python 标准库。

非目标（YAGNI）：密码找回、修改密码、删除账户、账户列表管理、邮箱验证、token 过期机制。

## 2. 方案选型

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. 账户上下文 + 路径解析函数 | 新增当前账户上下文（threading.local），各数据模块路径常量改为按上下文解析；已有路径参数的类按账户目录实例化 | **采用**：签名几乎不变，改动面最小 |
| B. 全显式依赖注入 | 数据路径逐层显式传参直至 ai_client 每条 LLM 调用链 | 弃：几十处签名改动，回归风险大 |
| C. 单活跃账户全局态 | 进程只认最后登录账户 | 弃：同机双浏览器登录不同账户会串号，违背隔离本意 |

线程传播要点：全项目仅 `recommender.py` 两处 ThreadPoolExecutor 提交的闭包会丢上下文，需显式捕获并恢复；`config_store.py` 的手动登录 worker 只写全局 login_state，无需传播。

## 3. 账户模型与存储

- 新模块 `core/account_manager.py`；全局账户表存项目根 `accounts.json`：

```json
{"accounts": {"<用户名>": {"username": "", "email": "", "password_hash": "", "salt": "", "created_at": "", "token": "", "token_time": ""}}}
```

- 密码：`sha256(salt + 密码utf-8)` 十六进制加盐哈希（hashlib + os.urandom(16) 生成 salt），绝不存明文。
- 注册校验：用户名 2-20 字符、不含空格、全局唯一；邮箱含 `@` 基础格式校验、全局唯一；密码非空。校验通过即创建成功并**直接签发 token（注册即登录）**。
- 登录：用户名+密码校验通过签发新 token（uuid4 hex），持久化进 accounts.json，服务重启后仍有效。
- 退出：清除该账户 token，旧 token 立即失效。
- 持久化：RLock 串行化 + 临时文件 `os.replace` 原子写；文件损坏备份为 `.broken` 后按空表处理（沿用 session_store 模式）。

## 4. 数据隔离布局

- 每账户一个目录 `accounts/<用户名>/`，内含 8 个文件：`user_profile.json`、`orders.json`、`virtual_cart.json`、`shopping_list.json`、`chat_sessions.json`、`user_center.json`、`api_key.json`、`search_history.json`。
- 保持全局（留在项目根）：`login_state.json`、`mock_products.json`、`scrape_cache.json`。
- 路径解析规则：
  - 模块级固定路径常量（`core/session_store.py`、`core/shopping_list.py`、`core/user_center.py`、`core/ai_client.py`、`core/product_searcher.py` 的 search_history）改为「按当前账户上下文解析」的内部函数；无账户上下文时回落项目根旧路径。
  - 已有路径参数的类（`ProfileManager`、`VirtualCart`、`OrderManager`）由 `ChatSession` 按账户目录传参实例化。
  - `ai_client`：按账户维护配置缓存字典（键=用户名），`get_config()` 内部经上下文取当前账户配置；优先级保持 环境变量 > .env > 账户 api_key.json；各账户的成功/失败统计随各账户配置独立。
- web_server：`SESSIONS` 会话缓存键由 `sid` 改为 `(用户名, sid)`；每账户激活会话由该账户自己的 `chat_sessions.json` 的 `active_id` 承载；每会话锁表键同步改。

## 5. 鉴权 API 与请求流

- 新增端点：
  - `POST /api/auth/register` `{username, email, password}` → `{ok, token, username}`；校验失败返回具体原因（用户名不合法/已存在、邮箱不合法/已存在等）。
  - `POST /api/auth/login` `{username, password}` → `{ok, token, username}`；失败统一提示「用户名或密码错误」。
  - `POST /api/auth/logout` → 清 token。
  - `GET /api/auth/me` → `{ok, user: {username, email, created_at}}`。
- 公开端点（免 token）：上述 auth 四个、`GET /api/health`（未登录时仅返回基础存活信息，不带账户数据）、`/`、`/index.html`、`/resource/*`。
- 其余全部既有端点：要求请求头 `X-Auth-Token`；缺失或无效 → 401 `{ok:false, error:"未登录"}`；端点内部逻辑与响应结构不变。
- 请求分发流程（do_GET/do_POST 入口统一处理）：解析 token → 查账户 → 设置当前账户上下文 → 进入原处理器；处理结束不强制清理（线程来自线程池时由下次分发覆盖，闭包线程已在提交点显式传上下文）。
- 存量数据迁移：注册**第一个**账户时（accounts.json 此前为空），若项目根存在旧数据文件（含 api_key.json）→ 逐一原子移动进该账户目录；无旧文件则空白开始。之后注册的账户一律空白。

## 6. 前端（单文件 index.html 内）

- 登录/注册门：未持有效 token 时全屏遮罩卡片，登录/注册双 tab 切换；注册三字段（用户名/邮箱/密码），登录两字段（用户名/密码）；错误就地文案提示；成功后 token 与用户名存 localStorage（`sa_token` / `sa_username`）进入主界面。
- fetch 统一包装：全部请求自动附加 `X-Auth-Token`；收到 401 → 清 token → 弹出门。
- 导航栏：右侧当前用户名胶囊（Material Symbols `person` 图标），点开小菜单含「退出登录」；点击后清 token 回门页。
- 风格红线：无 emoji；图标一律 Material Symbols；配色随主题色系（含深色模式）。

## 7. 错误处理与边界

- token 无过期时间（本地单机）；同浏览器双标签页共用同一 token 互不影响；不同浏览器可同时登录不同账户（隔离正确性来源）。
- 账户体系任何异常（accounts.json 损坏、上下文缺失）不得阻塞已登录核心对话：对话/购物链路照常走规则兜底红线。
- 真实抓取链路不受影响：平台登录态仍全局共享；抓取克制、验证码交人工等规则原样保持。
- Key 安全红线不变：`/api/apikey` 返回的仍是脱敏 Key（前后 4 位）。

## 8. 测试计划

- 脚本级：注册（含各类校验失败）/登录/退出/401 拦截；双账户隔离互查（A 的购物车/订单/清单对 B 不可见）；首账户迁移（旧文件进入新账户目录且根目录不再残留）；重启服务 token 仍有效；API Key 按账户独立（A 设置的 Key 不出现在 B）。
- 浏览器实测：双账户轮流登录，走查界面切换、数据切换、退出再登录。
- 测试卫生：不进真实搜索链路（用 mock/演示数据），避开登录墙弹窗与会话污染。
