# 意图理解与按需搜索 — 设计方案

> 创建于 2026-09-16 12:35
> 对应问题疑惑区「待完成」：输入「对比一下第一款和第三款，哪个更适合跑步」被无视，
> 反而输出三款毫不相干商品。开发者核心诉求：**AI 助手要能正常分析理解用户、正常交互，
> 只有真正需要搜商品时才搜索**。

---

## 1. 问题与代码级根因

### 1.1 现象

上一轮推荐出三款鞋后，用户追问「对比一下第一款和第三款，哪个更适合跑步」——这是一句
典型的基于上下文的对比提问。期望：基于已推荐的两款商品作答。实际：走了搜索流程，
输出三款与鞋子毫不相干的商品。

### 1.2 代码级根因（本轮排查结论）

故障链有三环，前两环是直接死因，第三环是开发者指出的**系统性病灶**：

**环一：规则解析把对比句拆成了「指向某款 + 用途」的组合。**
`core/request_parser.py` `_parse_rules()`（core/request_parser.py:366）对该句的解析结果：

- 「跑步」命中用途词表（core/request_parser.py:416）→ `purpose = "跑步"`；
- 「第三款」命中 `_parse_rank` → `target_rank = 3`；
- 「更（适合）」虽在 adjust_markers 表（core/request_parser.py:437）里，但因
  require/exclude/price_max 全空，`is_adjustment = False`；
- 关键词提取与 LLM 增强可能再补进「跑步/跑鞋」类字段。

**环二：路由级联里「搜索」排在「问答」前面。**
`shopping_agent.py` 消息路由（shopping_agent.py:178-232）的顺序是：

```
4) parse() 解析
4.1) target_rank + 字段全空 → 确认下单（强意图短路）
4.2) is_adjustment 或（target_rank + 任一条件字段）→ 合并上一轮 → _flow_recommend【搜索！】
4.2.5) 疑问信号/泛词 → _try_free_qa 自由问答兜底   ← 排在两个搜索触发分支之后
4.3) 澄清门控
4.4) _flow_recommend【搜索】
```

「对比一下第一款和第三款」带着 `target_rank=3` + 解析出的字段走进 4.2 的
`adjust_like` 判定（shopping_agent.py:195）→ 被当成「第二款式调整」去重新搜索；
就算字段组合走了 4.1，也会错误生成订单草稿。**4.2.5 的问答兜底根本轮不到执行**——
这正是「输出了三款毫不相干商品」的完整路径。

**环三（系统性病灶）：路由没有「意图判定」层，搜索是默认出口。**
现行架构是「解析字段驱动的级联」：解析出什么字段就走对应分支，**没有任何一步先问
「这句话到底是提问、调整、还是新需求」**。问答只是末端一个「try 一下、失败就落回搜索」
的装饰品。第 10 轮（负向约束）、第 12 轮（展开句式）两次修补都是在给这个级联打补丁，
同类问题换个句式就会再犯——与开发者「程序写太死了」的判断一致。

### 1.3 附带发现

`_try_free_qa`（shopping_agent.py:286）即使被走到，失败时（LLM 关闭/超时/答出
NEED_SEARCH）也是静默返回 None 落回搜索级联——「问答失败 = 乱搜一通」，同样属于
「不必要就搜索」的病灶表现。

---

## 2. 目标与非目标

**目标**

1. 意图先行：每条消息先判定「这是什么意图」，再分派流程；**搜索必须持「新需求/调整」
   的证才准发生**。
2. 「对比/哪个好/值不值/第X款怎么样」类基于上下文的提问，一律基于会话材料作答，
   绝不触发搜索。
3. AI 不可用时问答有体面的规则兜底（数据对比卡/如实告知），而不是落进乱搜。
4. 既有行为零回归：买第X款、条件调整、模糊澄清、新需求搜索全部保持现状。

**非目标**

- 不做完整对话状态机重构（见方案 C，评估后舍弃）；
- 不扩权补抓任何数据（抓取克制红线不动）；
- 不改前端——本轮纯后端路由与解析层改造。

---

## 3. 方案比较

### 方案 A（推荐）：意图判定前置层——规则速判 + LLM 终判，问答优先于搜索

在既有命令短路之后、需求解析级联之前，建立统一意图判定，路由由「字段驱动级联」
改为「意图分派」。

- **规则速判（零成本、确定性）**：复用已有正则信号（疑问标记 `_QA_QUESTION_RE`、
  「第X款」引用、调整标记、购买动词+品类词）先分出确定情形。
- **LLM 终判（灰区兜智能）**：在**既有** `parse()` 的 LLM schema 上增加一个
  `intent` 枚举字段——不新增调用次数，一次 LLM 调用同时产出解析与意图。
- **LLM 失败/关闭 → 规则保守兜底**：凡带疑问信号且无「新需求硬标志」→ 走问答；
  问答答不了 → 规则数据对比卡/如实告知，**绝不搜索**。

优点：直击病灶；符合既定偏好「智能类需求 LLM 主路径、静态规则兜底」；解析+意图合一
不增加延迟；改动集中在路由段，回归面可控。
缺点：路由段改动比纯打补丁大，需完整回归。

### 方案 B：纯规则修补（第 10/12 轮同款打法）

在 4.2 前加一条「疑问信号 + 上一轮有推荐 → 先试问答」的短路。

优点：十几行搞定，当天完事。
缺点：仍是打补丁。疑问信号词表永远有漏（第 10、12 轮已经连续两次被「换个句式」
打脸），不解决「写太死」的根本病灶，大概率第 13 轮还会再来。**舍弃。**

### 方案 C：完整对话状态机重构

引入正式对话管理器（意图集/槽位/状态转移全量重构）。

优点：最彻底。
缺点：工程量与回归风险远超本项目体量（12 轮积累的行为全要重验），课程作业周期内
不可控。**舍弃。**

## 4. 推荐方案（A）详细设计

### 4.1 意图枚举与判定流水

新增意图枚举（四类，命令类消息已被既有前置短路处理，不进意图层）：

| 意图 | 含义 | 去向 |
|---|---|---|
| `BUY_RANK` | 买/确认第X款 | 既有强意图短路 → 订单草稿+支付提醒（不动） |
| `QA` | 基于上下文的提问/对比/评价咨询 | 问答流程（绝不搜索） |
| `ADJUST` | 调整上一轮条件再搜 | 既有合并+搜索（不动） |
| `NEW_SEARCH` | 新购物需求 | 既有澄清门控+搜索（不动） |

判定流水（三层，前者优先）：

1. **规则确定判**（零成本）：
   - `buy_first` 前缀命中 → `BUY_RANK`（即现有 `rank_buy_intent`，保留）；
   - 疑问信号 + 「第X款」引用（或有上一轮推荐）+ **无新需求硬标志** → `QA`；
   - 调整标记/条件变更 + 非疑问主导 → `ADJUST`；
   - **新需求硬标志**（品类词/商品词 + 购买/求购动词，或明确「推荐/搜一下/来点」
     + 品类词）→ `NEW_SEARCH`。硬标志优先级**高于**疑问信号——
     「有没有跑鞋推荐？」虽是问句但实质是新需求，仍走搜索。
2. **LLM 终判**（灰区）：规则两可或冲突时，由 `parse()` 内既有 LLM 调用的 schema
   新增 `intent` 字段定夺（`qa / adjust / buy_rank / new_search` 四选一，schema 中
   写明判据与示例）。不新增调用、不增加延迟。
3. **规则保守兜底**（LLM 关闭/失败）：有疑问信号 → `QA`；有调整标记+上一轮 →
   `ADJUST`；有需求字段 → `NEW_SEARCH`；全无 → 进既有澄清。

### 4.2 路由重构：意图分派

`shopping_agent.py` 4) 段改为：

```
4)  parse()（现携带 intent）
4.1) intent==BUY_RANK（含既有强意图短路）→ 确认下单
4.2) intent==QA → 问答流程（4.2.5 升级，见 4.3），永不落入搜索
4.3) intent==ADJUST 且有上一轮 → 合并+搜索
4.4) 其余按既有 4.3 澄清门控 / 4.4 推荐执行
```

核心变化：**问答从「末端 try」升格为「一等分支」**；搜索分支的准入由意图把守。

### 4.3 问答流程升级

1. **材料答疑（主路径）**：沿用 `_try_free_qa`（上次推荐简报 + 历史窗口 + 档案白名单）。
   `ai_client.answer_free_question_with_llm` prompt 增强：用户点名「第X款/第Y款」
   对比时，逐项对比价格/评分分项/适用性并给结论+理由；材料缺失的维度如实说明，
   绝不编造（既有红线条款保留）。
2. **NEED_SEARCH 重路由**：LLM 答 NEED_SEARCH 时不再无脑落回搜索——只有当消息
   同时带「新需求硬标志」才重判为 `NEW_SEARCH`/`ADJUST` 走搜索；否则视为 LLM
   判断失误，按问答失败处理。
3. **问答失败的规则兜底（关键新增，绝不搜索）**：
   - 可提取「第X款 vs 第Y款」时：输出**数据对比卡**——从上次推荐简报取两款既抓字段
     （名称/价格/总分/分项评分/标签）并列客观展示，附一句「AI 答疑暂不可用，以上为
     已抓取数据的客观对比；主观建议需启用 AI 后询问」，缺失字段如实标注「未抓取到」；
   - 提取不出或材料缺失：如实告知「当前会话没有可供回答的推荐记录」+ 引导语。

### 4.4 改动清单

| 文件 | 改动 |
|---|---|
| `core/request_parser.py` | `ShoppingRequest` 增加 `intent` 字段；`_parse_rules` 增加规则意图速判（疑问信号/第X款引用/新需求硬标志，复用既有正则）；`parse()` 合并 LLM `intent` 字段 |
| `core/ai_client.py` | 解析 schema 增加 `intent` 枚举与判据说明；`answer_free_question_with_llm` prompt 增强（点名对比逐项比、NEED_SEARCH 判据收紧为「明确要求搜新商品」） |
| `shopping_agent.py` | 路由段 4) 重排为意图分派；`_try_free_qa` 失败落点改造（对比卡/如实告知，绝不搜索）；NEED_SEARCH 重路由 |
| `temp/test_intent_routing.py` | 新增离线断言（见 4.5） |

前端 `index.html` 零改动；既有 `_merge_request`、`_apply_hard_filters`、澄清门控、
档案向导旁路全部保留原位，仅「准入」由意图层把守。

### 4.5 测试与验收

**离线断言（`temp/test_intent_routing.py`，LLM 关闭即可跑）**

1. 「对比一下第一款和第三款，哪个更适合跑步」（有上一轮推荐）→ intent=QA，全程零搜索；
2. 同句在 LLM 关闭时 → 输出数据对比卡（含两款客观字段 + AI 不可用附注），零搜索；
3. 「买第2款」→ BUY_RANK 短路，产出订单草稿（回归）；
4. 「第二款不要黑色的，换粉色，预算升到800」→ ADJUST 合并搜索（回归第 12 轮）；
5. 「买一双跑鞋，预算300」→ NEW_SEARCH 正常搜索（回归）；
6. 「有没有跑鞋推荐？」→ 新需求硬标志压过疑问信号 → 走搜索；
7. 「这双鞋值不值」无上一轮推荐 → 如实告知，零搜索；
8. LLM 返回 NEED_SEARCH 但消息无硬标志 → 不搜索，走问答失败兜底。

**既有回归**：`test_hard_filters` / `test_buy_rank_intent` / `test_adjust_negation` /
`test_dims_clarify` / `test_food_clarify` / `test_review_honest` / `test_profile_empty_save` /
`test_wizard_bypass` / `test_t4_parser` 全过。

**真机冒烟**（重启服务后，bug子 账号新会话）：先「买一双跑鞋……预算300」出推荐，再发
「对比一下第一款和第三款，哪个更适合跑步」→ 应得到基于两款真实商品的对比回答，
无任何新搜索；随后「第二款不要黑色的，换粉色」确认调整路径未受影响。

## 5. 红线对照

- **AI 全链路兜底**：意图判定三层流水，LLM 失败静默落规则速判；问答失败落规则对比卡，
  任何一层 AI 失效功能不中断。
- **数据真实性**：对比卡只用已抓字段，缺失如实标注；QA prompt 保留「材料中没有就答
  没有」条款。
- **抓取克制**：QA 路径零抓取，本方案实际**减少**无谓搜索次数。
- **支付红线/Key 安全/无 emoji**：不触碰；QA 与对比卡模板纯文字（AI 消息出口已有
  `strip_emoji` 净化）。

## 6. 风险与边界

- **误判 QA（想搜却答了）**：新需求硬标志优先级高于疑问信号 + LLM 终判灰区兜底；
  真机冒烟第 6 条专测此路径。
- **误判 NEW_SEARCH（想答却搜了）**：即本次事故路径；规则速判把「疑问+第X款引用」
  列为最高优先级 QA 信号，LLM intent 字段作为第二道防线。
- **对比卡体验**：AI 不可用时信息量有限——如实定位为「客观降级」，不冒充智能回答。
- **长句疑问**（>40 字）现状视为正常需求：该启发仅作用于规则速判，LLM 终判可翻案，
  不额外放宽长度阈值以免误拦真实搜索需求。
