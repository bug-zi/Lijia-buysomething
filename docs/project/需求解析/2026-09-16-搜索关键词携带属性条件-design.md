# 搜索关键词携带属性条件 — 设计方案

> 创建于 2026-09-16 17:47
> 开发者真机反馈：调整需求「第一款不要这种带有黑色元素的，换粉色+白色的，预算升到800」
> 后，网页搜索的搜索框里没有输入「粉色+白色」等关键信息，导致抓回的结果不是想要的。
> 2026-09-16 开发者选定：**方案 A**（规则组装器兜底 + LLM search_keywords 主路径）。

---

## 1. 问题与代码级根因

### 1.1 现象

首轮「买一双跑鞋，日常运动穿，透气轻便的，不要黑色，预算500以内」出推荐后，发调整
「第一款不要这种带有黑色元素的，换粉色+白色的，预算升到800」。系统重新搜索时搜索框
只输入了品类词（跑鞋），粉色+白色没有进搜索框，抓回的结果与颜色诉求不符。

### 1.2 代码级根因

用户的颜色诉求**被正确解析到了**（进 `require_tags`，硬过滤也会执行），但被一条旧
设计决定**有意挡在了搜索框之外**：

1. **解析层主动剔除颜色词**：`core/request_parser.py` `_extract_keyword` 中
   （core/request_parser.py:714-718）写明「颜色词不进搜索关键词：颜色已由要求/排除
   标签承接、由硬过滤层执行，且『粉色+白色』这类多颜色无法拼进单一搜索词」；
   require_tags 追加属性词时同样跳过颜色（core/request_parser.py:750）。
   因此 `req.keyword` 永远不含颜色。
2. **搜索词直接取 req.keyword**：`shopping_agent.py` `_flow_recommend`
   （shopping_agent.py:484）`keyword = req.keyword or req.category`，颜色无处可进。
3. **增量替换的定向搜索同病**：`_flow_adjust_replace._slot_pick`
   （shopping_agent.py:595）只拿被指商品的 `category`（或 merged keyword）当搜索词，
   同样不带颜色。
4. **硬过滤作用在极小窗口上**：每平台默认仅抓前 6 条（最多 10 条，
   shopping_agent.py:492-493）。搜索框只有「跑鞋」时，窗口里大概率一条粉/白都没有
   ——要么全被「颜色不符」剔光，要么「未标注颜色」的卡（含黑鞋）混进结果。
   搜索框缺词是因，硬过滤独木难支是果。

附注：当年注释里「多颜色无法拼进单一搜索词」的理由不成立——淘宝/京东/拼多多搜索框
天然支持空格分词的多词查询（web_scraper.py:863 `search_platform` 将关键词整串
quote 进 URL 的 keyword/q 参数）。

### 1.3 病灶定性

「正向可搜属性（颜色等）只做后置过滤、不做前置召回」——在限量抓取（≤10 条/平台）的
约束下，后置过滤的召回前提不成立。修复方向：**正向约束进搜索框（提召回），否定约束
进硬过滤（保正确）**，两者分工不变。

## 2. 目标与非目标

**目标**

1. 每次真实搜索（新需求、调整全量重搜、增量替换定向搜）的搜索框查询串必须携带
   「品类词 + 尺码 + 正向颜色要求」；LLM 可再补软属性（透气/轻便等）。
2. 否定约束（不要黑色）、预算数字、条数**绝不进搜索框**，仍由硬过滤层执行。
3. AI 不可用时规则组装器兜底，功能永不因 AI 失效中断。
4. 既有行为零回归：`req.keyword` 字段语义不变（纯品类核心词），硬过滤颜色 OR 语义、
   「未标注颜色」候补计数、澄清门控、意图路由全部不动。

**非目标**

- 不增加任何抓取量（仍单次查询、每平台 ≤10 条，抓取克制红线不动）；
- 不做「零结果自动去色重搜」的降级二段搜索（方案 C，舍弃，列为后续增强）；
- 不扩充颜色词表（「香槟色」等冷门色现状即不识别，维持现状）；
- 不改前端 `index.html`。

## 3. 方案比较

### 方案 A（已选定）：搜索词组装器（规则兜底）+ LLM search_keywords（主路径）

- **规则组装器** `compose_search_query(req)`：品类词 + 尺码 + require_tags 中颜色词
  拼成查询串（如「跑鞋 42码 粉色 白色」），确定性、零成本。
- **LLM search_keywords**：在**既有** `parse()` 调用的 schema 上增加
  `search_keywords: string|null` 字段（不新增调用次数、不增加延迟），AI 按上下文
  给出「最适合搜索框的查询串」，软属性（透气/轻便）也能带进搜索框；产出与规则组装
  结果过**同一个校验器**，非法一律拒收。
- 在 `_flow_recommend` 与增量替换 `_slot_pick` 两处搜索点统一接入。

优点：直击病灶（颜色进搜索框）；软属性受益；符合「智能类需求 LLM 主路径、静态规则
兜底」既定偏好；零新增 LLM 调用。缺点：新增一个派生字段与校验器，回归面含搜索链路。

### 方案 B：纯规则组装器

只做规则层（品类+尺码+颜色），不动 LLM schema。改动最小，但透气/轻便类软属性永远
进不了搜索框，词的取舍写死。**作为 A 的组成部分保留，单独采用则智能性不足。舍弃。**

### 方案 C：A + 零结果自动去色重搜

颜色进搜索框后若筛完为空，自动去掉颜色词再搜一轮。召回最稳，但失败即多一轮抓取，
与抓取克制红线精神相悖，状态机复杂。**舍弃**（列为后续增强候选，不立项）。

## 4. 选定方案（A）详细设计

### 4.1 校验器与组装器（core/request_parser.py，模块级纯函数）

- `validate_search_query(q: str) -> Optional[str]`：查询串准入校验——含否定词
  （不要/避开/别/非/讨厌…）、预算数字碎片（预算/升到/加到/以内/以下/左右/裸数字）、
  「第X款」指代、超长（>24 字符）→ 返回 None；通过则返回空白归一后的串。
  规则组装结果与 LLM 产出**共用同一校验**，不对称放行。
- `compose_search_query(req: ShoppingRequest, base: Optional[str] = None) -> str`：
  1. 基底 = `base or req.keyword or req.category or "商品"`（增量替换传被指商品
     `category` 作 base）；
  2. 拼尺码（有 `req.size` 则加「N码」）；
  3. 拼 require_tags 中命中 `_COLOR_WORDS` 的颜色词（去重保序、全量拼入，
     「粉色 白色」原样进框）；
  4. 非颜色 require 属性**规则路径不拼**（透气/轻便留给 LLM 主路径，避免
     「日常运动穿」类碎片污染）;
  5. 产物过 `validate_search_query`；超限/非法时**从尾部逐个丢属性词**（颜色先于
     尺码被丢）重试，保基底与尺码，绝不一次性清空回退。
- 放置理由：request_parser 已持有 `_COLOR_WORDS`（core/request_parser.py:76），
  `_merge_llm_json` 的同源校验也在本模块，避免 shopping_agent ↔ request_parser
  循环导入（shopping_agent.py:23 已从本模块导入多个符号，零新增依赖）。

### 4.2 LLM search_keywords 字段（主路径，零新增调用）

- `ai_client.parse_shopping_request_with_llm` 的 sys_prompt（core/ai_client.py:466-486）
  增加一行字段说明：`search_keywords: string|null` ——「最适合放进电商搜索框的完整
  查询串：品类词 + 可搜的正向属性（颜色/透气/轻便等）；严禁包含否定词（不要X）、
  预算数字、条数、『第X款』指代；没有把握就填 null」。
- `ShoppingRequest` 增加 `search_keywords: Optional[str] = None`。
- `_merge_llm_json`（core/request_parser.py:801）捕获该字段：**过校验器才写入**，
  非法/null 保持 None（不覆盖规则层——本字段规则层不产出，仅 LLM 产出）。

### 4.3 两处搜索点统一接入（shopping_agent.py）

- `_flow_recommend`（shopping_agent.py:484）：
  `keyword = req.search_keywords（过校验） or compose_search_query(req) or "商品"`，
  替换现行 `req.keyword or req.category`。尺码拼词逻辑并入组装器，原处删去。
- `_flow_adjust_replace._slot_pick`（shopping_agent.py:595）：
  `kw = compose_search_query(slot_req, base=slot_old.category or ...)`，定向搜索
  从此带上颜色；「颜色命中优先」的 `_pref_key` 排序保留（召回与择优双保险）。
- **合并防陈旧**：`_merge_request`（shopping_agent.py:921）增加
  `merged.search_keywords = delta.search_keywords（有效时）else None`——**不沿用
  base**：颜色条件已变，旧查询串必须作废，由组装器基于 merged 全量条件现场重拼。
- 登录墙「继续抓取」续跑路径复用同一 req 对象 → 同一查询串，天然一致。
- 如实告知/失败文案中的「搜索关键词：`{keyword}`」展示改用实际下框查询串。

### 4.4 不变式（正确性仍由硬过滤保证）

- `_apply_hard_filters`（shopping_agent.py:702）颜色 OR 语义、未标注颜色候补计数、
  排除词/预算过滤**原样保留**——搜索框带颜色只提召回，不承担正确性。
- `_extract_keyword` 的颜色剔除**保留**（req.keyword 维持纯品类核心词语义），
  仅修订 core/request_parser.py:714-718 与 :750 两处注释为「颜色不进 req.keyword
  字段；由 compose_search_query 在搜索时拼入查询串」。
- `rank_buy_intent` 短路、澄清门控、意图路由、Mock 模式（查询串以品类词开头，
  `_guess_category` 匹配不受影响）全部不动。

### 4.5 改动清单

| 文件 | 改动 |
| --- | --- |
| `core/request_parser.py` | 模块级 `validate_search_query` / `compose_search_query`；`ShoppingRequest.search_keywords` 字段；`_merge_llm_json` 捕获（过校验才写）；:714/:750 注释修订 |
| `core/ai_client.py` | `parse_shopping_request_with_llm` schema 增加 `search_keywords` 字段与判据（其余不动） |
| `shopping_agent.py` | `_flow_recommend` 与 `_slot_pick` 搜索词改走组装器；`_merge_request` 合并 search_keywords（防陈旧置 None）；失败文案展示实际查询串 |
| `temp/test_search_query.py` | 新增离线断言（见 4.6） |

前端零改动；`index.html` 不触碰。

### 4.6 测试与验收

**离线断言（`temp/test_search_query.py`，LLM 关闭即可跑）**

1. 组装器：req(keyword=跑鞋, size=42, require=[透气, 粉色, 白色]) → 「跑鞋 42码
   粉色 白色」（透气不被规则路径拼入）；
2. 校验器拒收：「跑鞋 不要黑色」「跑鞋 预算800」「第2款 跑鞋 粉色」、超 24 字符串
   → 全部 None；
3. search_keywords 有效（如「跑鞋 透气 轻便 粉色」）→ 优先于规则组装；null/非法 →
   落规则组装器；
4. 合并防陈旧：delta 带有效 search_keywords → merged 采用；delta 无 → merged 为
   None（绝不沿用 base 的旧串）；
5. 增量替换 `_slot_pick`：mock searcher 记录入参，断言定向搜索词含颜色词；
6. 组装器产物以品类词开头（Mock `_guess_category` 命中不受影响）。

**既有回归**：`test_search_query` 之外，`test_intent_routing`（12 条）、
`test_adjust_negation`、`test_hard_filters`、`test_buy_rank_intent`、
`test_t4_parser` 等全部既有测试照常全过；其中涉及搜索词的断言按新查询串同步修订。

**真机冒烟**（重启服务后交开发者执行，测试不进真实搜索链路）：跑鞋需求出推荐 →
发「第一款不要这种带有黑色元素的，换粉色+白色的，预算升到800」→ 浏览器实际搜索框
应输入含「粉色 白色」的查询串，抓回结果以粉/白为主；尾注如实展示实际搜索词。

## 5. 红线对照

- **抓取克制**：不新增任何抓取量——每次搜索仍是单次查询、每平台 ≤10 条、不翻页；
  方案 C 的多轮重搜已舍弃。
- **AI 全链路兜底**：LLM 关闭/失败/search_keywords 为 null 或非法 → 规则组装器接管，
  功能永不中断；校验器对 LLM 产出与规则产物一视同仁。
- **数据真实性**：给用户展示的「搜索关键词」一律为实际下框查询串，如实呈现。
- **无 emoji / 支付红线 / Key 安全**：不触碰。

## 6. 风险与边界

- **LLM 查询串品类漂移**（脑补「女款」「透气跑步鞋」等）：schema 已有「严禁脑补合并
  新品类」条款延续约束，校验器只做结构校验不做语义校验；最坏情形是搜索质量下降，
  正确性仍由硬过滤兜住；真机冒烟覆盖。
- **平台对多词查询的召回差异**：京东/淘宝/拼多多均支持空格分词，但个别词组合可能
  召回偏少 → 落入既有「未找到符合条件」如实告知路径（可放宽条件重试），不做自动
  降级重搜。
- **冷门颜色不识别**（如「香槟色」不在 `_COLOR_WORDS`）：既有限制，本轮不扩表。
- **旧会话兼容**：`search_keywords` 为新增可选字段，旧持久化数据缺省 None，组装器
  照常工作，无迁移需求。
