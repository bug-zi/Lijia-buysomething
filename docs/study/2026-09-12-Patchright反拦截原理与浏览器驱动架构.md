# Patchright 反拦截原理与浏览器驱动架构（为什么现在能拿到真实数据了）

> 创建于 2026-09-12 03:35 · 适用于配置库上线后的 dev 分支代码（web_scraper.py 为 Patchright 基座 + 真实 Chrome channel + 持久化 profile）

本文整理四个问答：①Patchright 为什么不容易被淘宝/天猫拦截；②「AI 自动开浏览器」是谁的能力；③如何理解启动架构那句话；④怎么向同伴解释旧方案为什么不行、新方案为什么行。

---

## 一、Patchright 只是爬虫脚本，为什么不会被淘宝/天猫拦截？

先纠正前提：**不是「不会被拦截」，是「更难被发现」**。淘宝扫码登录卡「请在手机上确认」那几次，就是平台风控在起作用。

**1. 网站怎么发现你是脚本？**
网页 JS 看不到你用了什么库，它只能检测浏览器运行时留下的「指纹」和「痕迹」。原版 Playwright/Selenium 这类 CDP（Chrome DevTools Protocol）驱动的框架有一批经典破绽：

| 破绽 | 说明 |
|---|---|
| `navigator.webdriver = true` | WebDriver 协议标志，一行 JS 就能读 |
| `Runtime.enable` 侧信道 | Playwright 要开这个 CDP 域来执行 JS，页面可用 `console.debug` 的堆栈差异探测到它开着（Patchright 文档里的著名检测手段） |
| 环境指纹残缺 | 无痕全新会话没有历史 Cookie/本地存储；捆绑 Chromium 的特征与大众浏览器不同 |
| 行为特征 | 点击瞬间到达、无鼠标轨迹、请求节奏机械 |

风控（阿里系的 baxia/无痕验证等）把这类信号**加权打分**：分高就弹滑块、验证码，或干脆整页变成登录页。京东搜索未登录整页变登录页、淘宝登录卡在确认环节，都是打分过高的表现。

**2. Patchright 做了什么？**
它是 Playwright 的**补丁版 fork**，在驱动层（不是网页 JS 层）抹掉自动化框架自身的指纹：

- 不再调用 `Runtime.enable`（改用 ShadowDOM/绑定注入的其他方式），堵死最著名的侧信道；
- 隐藏 `navigator.webdriver` 等自动化标志；
- 修补其他 CDP 泄露点。

关键区别：网上常见的 stealth 插件是「JS 层伪装」——往页面里注入覆盖脚本，可以被「检测伪装本身」的手段（如检查原生函数是否被覆写）识破，甚至注入行为本身反而加分（本项目 260912 凌晨就实测过：注入 stealth 反而导致京东扫码一直失败，Patchright 下停用注入才成功）。Patchright 是驱动级修补，页面 JS 层面不留伪装痕迹。

**3. 但 Patchright 只消除一类信号**。风控总分还包含：IP 信誉、账号行为历史、操作频率、环境一致性。所以本项目是**组合拳**，每一层对应一类信号：

| 层 | 项目里的做法 | 压制哪类信号 |
|---|---|---|
| 驱动 | Patchright（缺失回退原版 Playwright） | 框架指纹 |
| 浏览器 | 真实 Chrome channel 优先，不用捆绑 Chromium | 环境指纹 |
| 会话 | `.browser_profile` 持久化 + **人工扫码登录** | 无历史/机器会话 |
| 行为 | 随机延迟 + 慢速滚动 | 机械节奏 |
| 频率 | 每平台每次 ≤10 条、不翻页不遍历、仅用户主动发起 | 高频爬取 |
| 兜底 | 遇滑块/验证码暂停交还人工，绝不绕过 | ——（红线：不绕风控） |

## 二、「AI 自动开浏览器搜索」是 Patchright 的功能还是 browser-use？

**都不是 browser-use，浏览器操作也不是「AI」在操作。**分工是：

```
你的需求「买连衣裙 200 以内」
   ↓  规则代码解析（正则/词典，LLM 仅可选增强）
关键词/预算结构化数据
   ↓  本项目自己写的 web_scraper.py 规则代码
拼搜索 URL → Patchright 开浏览器 → 跳转 → 慢速滚动 → 按 selector 逐卡片提取
   ↓  结构化商品数据（拿不到的字段留空，绝不编造）
打分排序 → TOP3 → LLM（可选）润色点评
```

- 打开浏览器、导航、抓 DOM 是 **Playwright/Patchright 的基础能力**（它们本来就是浏览器自动化库）；
- 「去哪搜、搜什么、抓哪些字段、抓几条」是**项目的确定性规则代码**；
- browser-use 那种「LLM 看屏幕截图、逐步决策点哪」的全自动 agent 在技术选型时**明确否决**了：每一步都要 LLM 决策，违反「LLM 仅增强、规则引擎兜底」红线，token 成本也高；
- LLM 在链路里只做需求解析增强和推荐文案润色，失败就静默回退规则引擎。

一句话：**Patchright 是「手和眼」，项目代码是「大脑和流程」，LLM 只是「文案助手」**。

## 三、如何理解「Patchright 驱动 → 真实 Chrome（channel 优先）+ .browser_profile 持久化会话」

逐段拆：

- **Patchright 驱动**：开浏览器的「遥控器」用补丁版 Playwright，遥控指令的痕迹被抹掉；Patchright 未安装时自动回退原版 Playwright——功能一样，只是更容易被风控识别（可选依赖，不影响启动）。
- **真实 Chrome（channel 优先）**：不用 Playwright 自带的 Chromium（捆绑版的指纹特征明显、不像大众在用的浏览器），而是探测你电脑上日常安装的 Chrome（`channel="chrome"`，找不到再试 Edge），驱动它来干活。它的全部指纹和你平时上网的浏览器一致。
- **.browser_profile 持久化会话**：普通自动化每次都开一个「全新无痕浏览器」，啥历史都没有；本项目把浏览器的用户数据目录固定到项目下的 `.browser_profile` 文件夹，Cookie、登录态、localStorage 全部落盘。下次启动直接加载——**登录过一次淘宝，之后几天抓取自动带着登录态，短期免扫码**。配置库里管理的登录态就是这套 profile 的状态元数据（Cookie 本体始终只在这个目录里，数据库不存在，`login_state.json` 也只存状态不存 Cookie）。

三层合起来的效果：在平台眼里，这≈一个真人日常在用的 Chrome——有历史、有登录态、由人类亲手扫码登录，只是「手」是脚本。

## 四、怎么向同伴解释「旧方案不行、现在行了」

论证链（每一步都有对应实测记录，见 `docs/log/260912.md`）：

1. **旧方案的问题不是「不想抓」，是「一抓就死」**：原版 Playwright 指纹泄露 → 京东搜索未登录整页变登录页、淘宝登录扫码一直不成功（stealth 注入反而暴露自动化特征）。
2. **会话从「一次性」改「持久化」**：旧方案每次全新无痕会话，永远没登录态；现在登录一次写入 profile，短期免扫码。且登录由**用户本人扫码**完成，程序绝不过手账号密码——凭据始终只在用户自己的浏览器会话里产生。
3. **页面适配**：京东 2026-09 已改版新版搜索页（无 `<a>` 的插件化卡片），selector 按实测 DOM 更新并多候选兜底——「能拿到」不只剩风控问题，还有解析问题。
4. **结果可验证**：京东真实搜索冒烟返回 6 条带图真实商品（价格/销量/店铺/链接全就位），每条带 `data_source` 标注；抓不到时如实告知并回退「粘贴链接」路径，绝不编造。
5. **克制的边界**（这是能长期「行」的前提，也是向同伴强调的红线）：仅用户主动发起、每平台 ≤10 条、不翻页不遍历、不绕验证码、不做过手密码的自动登录、登录墙交还人工。

给同伴的一句话版本：**「不是爬虫变强了，而是把自动化伪装成真实使用习惯（真 Chrome + 持久化会话 + 人类扫码），再把抓取量控制在正常人范围内；风控看见了，但打不出高分。」**
