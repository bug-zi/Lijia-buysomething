# Cookie 存储位置与安全边界（登录态到底存在哪、会不会泄露）

> 创建于 2026-09-12 03:48 · 适用于配置库上线后的 dev 分支代码
> 姊妹篇：[Patchright 反拦截原理与浏览器驱动架构](./2026-09-12-Patchright反拦截原理与浏览器驱动架构.md)

三个问题：①配置库登录后 Cookie 具体存在哪；②有没有泄露风险；③为什么装了 Patchright 就能获取信息了。

---

## 一、Cookie 具体存在哪？

**存在项目根目录的 `.browser_profile/` 文件夹里**——它是「浏览器的用户数据目录」，和你平时 Chrome 的个人数据目录是同一种东西。本项目启动浏览器时用 `launch_persistent_context(user_data_dir=".browser_profile")`，淘宝/京东登录后浏览器把会话凭据写进这个目录：

| 内容 | 实际位置 | 加密情况 |
|---|---|---|
| Cookie（含京东 `pt_key`、淘宝会话票据） | `.browser_profile/Default/Network/Cookies`（SQLite 数据库） | 值经 Chromium 加密（Windows 用 DPAPI，**绑定当前 Windows 账户**，换账户/换机器解不开） |
| localStorage / IndexedDB（平台另存的会话令牌） | `.browser_profile/Default/Local Storage/leveldb` 等 | 通常未加密，但受文件系统权限保护 |
| 缓存、指纹相关本地状态 | `.browser_profile/` 其余子目录 | ——（整个目录实测约 305MB） |

注意区分两层：

- **Cookie 本体**：只存在于 `.browser_profile` 里，由浏览器自己读写、自己加密；项目代码**从不读取、保存、导出 Cookie 值**。
- **`login_state.json`（配置库的状态文件）**：只有 `平台/状态/检测时间/来源/备注` 五个元数据字段，**没有任何 Cookie 内容**（`config_store.py` 自测里有敏感字段断言：cookie/token/pt_key/unb 等字样出现即失败）。

代码里唯二接触 Cookie 的地方（可 grep 验证）：①淘宝登录检测——查「是否存在名为 `unb` 的 cookie」，只看名字、不读值；②清除登录态——按域名读 cookie 的名字/域/路径元数据用于**删除**。抓取流程本身完全不碰 Cookie，浏览器自动带上。

## 二、会不会有泄露风险？

按泄露途径逐条过：

| 途径 | 风险 | 依据 |
|---|---|---|
| **git 提交泄露** | 无 | `.gitignore` 已含 `.browser_profile/`、`login_state.json`，不会入库 |
| **网络被别人访问** | 无 | 服务只绑定 `127.0.0.1`，局域网/外网连不上；`/api/login` 接口只回传状态元数据，永不回传凭据 |
| **被传给第三方** | 无 | Cookie 只会被浏览器在访问 taobao.com/jd.com 时带给出货平台自己——和你平时用浏览器购物同一性质；项目没有任何把 Cookie 发往别处的代码 |
| **本机其他软件窃取** | 有，但**与风险同源** | Cookie 值用 DPAPI 加密，绑定你的 Windows 账户；**同账户下的恶意程序理论上可解密**——但你日常使用的 Chrome/Edge 面临的完全是同一个风险（它也把所有网站登录态存在同样机制的目录里），本项目没有扩大攻击面，反而更小：这里只有淘宝/京东的购物会话，没有你的邮箱/网盘/支付后台 |
| **电脑被他人物理使用** | 同上 | 建议：锁屏、专用系统账户；或不用时在配置库点「清除登录态」（立即作废会话，等价于退出登录） |

**降低暴露面的既有设计**：配置库与抓取互斥防 profile 抢占；清一下「清除登录态」就能立即作废；`login_state.json` 无敏感内容可随意外传也不泄露凭据。

一句话：**登录态的存放方式与你日常浏览器完全相同，风险相同；项目自身不留副本、不回传、不导出，且 Git/网络两条最常见的泄露路径已被掐断。**

## 三、为什么「配置了 Patchright」就能获取信息了？

准确说：**Patchright 不是钥匙，它不「解锁」任何东西，也不绕过任何验证**。获取信息是三个条件缺一不可：

1. **门票：登录态**（决定「能不能看」）。淘宝/京东搜索页**强登录**——未登录时京东整页直接渲染成登录页，什么商品都没有。你在配置库扫码后，会话写入 `.browser_profile`，之后抓取浏览器自动带上，看到的才是「已登录用户的商品列表页」。实测反例：装了 Playwright 但没登录，京东搜索照样是登录墙（260912 凌晨日志有记录）。
2. **隐形：Patchright**（决定「看不看得到、会不会被弹验证」）。页面由真实浏览器渲染，商品列表是 JS 动态加载的（所以 requests 拿不到）；Patchright 保证「脚本驱动浏览器」这个动作本身不被风控加权——不给自动化痕迹加分，页面才能正常加载渲染，而不是被替换成滑块/登录墙。
3. **读取：selector 解析**（决定「拿得到数据吗」）。渲染出来的 DOM 里，项目用多候选 CSS selector 把卡片里的名称/价格/图片/店铺/销量逐项提取，取不到的字段留空，绝不编造。

所以正确的因果链是：**登录态给了你看商品的资格，真实浏览器给了你渲染页面的能力，Patchright 让「脚本在看」这件事不被风控扣分，selector 让脚本能把看到的东西变成结构化数据。** 配置 Patchright 只是补齐了其中「不被扣分」那一环——它起作用的每一步，都建立在登录态存在、不绕风控的前提上。
